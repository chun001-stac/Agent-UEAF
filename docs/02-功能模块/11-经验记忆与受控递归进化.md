# 11｜经验记忆与受控递归进化

Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 模块定位

本模块是 UEAF V1 的 **Controlled Evolution Kernel**。它把生产运行、评测、成本和业务反馈中的结构化证据转化为有限、可审计、可停止的改进循环。

V1 主链：

```text
Evidence / Opportunity
  -> operational response if urgent
  -> Trigger Gate
  -> EvolutionTrigger
  -> bounded EvolutionRun
  -> Diagnosis / Repair Router
  -> sparse MutationProposal when justified
  -> GenomeManifest candidate
  -> existing ReleaseCandidate
  -> existing Eval / Release Governance
  -> Production Feedback
```

本模块不是另一个 Agent Runtime，也不是常驻“自我反思 Agent”。没有有效 Trigger 时，不应进行持续演化推理。

Evidence 采集遵循：

> **模块 02–08 产生事实，模块 09 采集/采样/聚合，模块 11 只消费 Projection 与按需引用。**

长期修复遵循：

> **基层模块负责发现事实和即时止血；模块 11 负责诊断与选择最小长期修复。**

详细规范：

- `../01-核心规范/07-V1最小Evidence采集规范.md`
- `../01-核心规范/08-V1问题诊断与最小修复规范.md`

## 2. V1 一等对象

模块 11 在 V1 只拥有以下演化语义：

- `EvolutionTrigger`；
- `EvolutionRun`；
- `GenomeManifest`；
- `MutationProposal`；
- `EvolutionAuthorityPolicy`。

候选、评测、预算、发布、工件、事故响应、原始 Evidence、Diagnosis 和 Repair 不重新定义为新 Domain：

| 能力 | 复用/表达方式 |
|---|---|
| Candidate | 模块 10 `ReleaseCandidate` |
| Eval | 模块 08 `EvalConfig` / `EvalRun` / `EvalResult` |
| Security Gate / immediate security action | 模块 07 |
| Telemetry collection / sampling / aggregation / retention | 模块 09 |
| Operational response / SLO / fallback | 模块 09 |
| Rollback / Release | 模块 08 / 09 既有发布控制 |
| Tool-side containment / reconciliation | 模块 05 Tool Gateway |
| Budget | 既有 Budget Domain / Budget Ledger |
| Artifact / Bundle | 模块 10 / Registry |
| Diagnosis / RepairLevel / RepairHistory | 内部策略、Projection、metadata |

模块 11 不拥有第二套 `CandidateRelease`、`EvaluationSuite`、`EvolutionBudget`、`FitnessRecord`、`LineageGraph`、Incident、OperationalResponse、Trace/Metric/Log/Eval/Action 或 Evidence 数据平台真相源。

## 3. 与现有模块的边界

| 模块 | 协作 | 模块 11 不负责 |
|---|---|---|
| 02 Runtime/State | 读取 Run outcome/state summary refs；可诊断 runtime/adapter 问题 | 不成为 Run State Writer，不原地改运行状态语义 |
| 03 Model | 读取 token/cost/latency/error/invocation refs；可修 Prompt/Model Route | 不复制 Prompt/Response 全量历史 |
| 04 Context/RAG/Memory | 读取 retrieval/context summary 与 manifest refs；可修 Context/Retrieval/Memory Policy | 不拥有 `MemoryRecord`，不放宽 ACL，不复制所有 chunks |
| 05 Tool/MCP | 读取 Tool failure/receipt/outcome certainty refs；可提出 Tool/Route Candidate | 不绕过 Tool Gateway；unknown 必须先 reconciliation |
| 06 Workflow/Multi-Agent | 读取 fan-out/handoff/node failure summary；可提出 Workflow Mutation | 不修改正在运行的 WorkflowRun |
| 07 Identity/Security | 接收安全事件/mitigation 引用并受安全门禁约束 | 不签发权限，不取代 incident response，不自动扩大权限 |
| 08 Eval/Release | 提交 ReleaseCandidate，消费 EvalResult，引用 rollback/release 事实 | 不重建 Eval，不签发 ReleaseManifest |
| 09 Production/Observability | 消费 Run Summary、窗口、Fingerprint、Metric/Cost/SLO/Trace refs | 不建设并行 collector/store，不取代 SRE |
| 10 Developer/Adapter | 使用 Sandbox/Bundle Builder 构建 Candidate | 不绕过 Developer/Release 流程 |

## 4. 逻辑组件

V1 推荐逻辑组件；可以同进程实现，不意味着独立服务。

| 组件 | 职责 |
|---|---|
| Evidence Projection Reader | 查询模块 09/08/05/04 等 Projection 与 refs |
| Signal / Opportunity Detector | 从 Summary/Metric/Eval/Security/Fingerprint 识别 Trigger Candidate |
| Trigger Gate Engine | 判断 evidence、relevance、mutable surface、mitigation、novelty、value、cooldown |
| Evidence Expander | 按需读取有界 A/B/C 对照样本 |
| Evolution Coordinator | 创建并推进 `EvolutionRun` |
| Diagnosis / Repair Router | 识别 root cause、选择 Repair Target 与最小 Repair Level |
| Genome Registry | 保存 `GenomeManifest` 与版本引用 |
| Strategy / Mutation Proposer | 在授权 scope 内产生有限 `MutationProposal` |
| Working Set Builder | 基于 Trigger + Diagnosis + Expansion 生成有界上下文 |
| Candidate Bridge | 调用模块 10 生成 `ReleaseCandidate` |
| Selection View | 基于 EvalResult 等证据比较候选，不成为第二真相源 |

V1 不建设独立 Evidence Collector、Repair Service、RepairHistory Service、GenePool Service、Species Service、Lineage Service 或 Ecosystem Fitness Service。

## 5. 即时运行响应与 Evolution Response

发现问题后，系统 MUST 先判断是否需要即时保护生产，而不是默认启动自我修改。

```text
Observed signal
  ├─ urgent -> Operational Response
  │             rollback / fallback / isolate / degrade / kill / reconcile
  │
  └─ evidence -> Trigger Gate -> Evolution Response
```

- Operational Response：解决“现在怎么办”；
- Evolution Response：解决“未来是否值得改变自己”。

模块 11 MUST NOT 为等待 EvolutionRun 而延迟必要的安全隔离、回滚、fallback、降级、限流、reconciliation 或 kill switch。

### 5.1 P0-P3

| Priority | 典型场景 | 即时动作 | Evolution |
|---|---|---|---|
| P0 | 数据泄漏、越权、高风险错误动作 | isolate / rollback / kill | 立即或高优先 Trigger |
| P1 | 大面积质量崩溃、系统性 Tool/Model 失败 | fallback / degrade / rate-limit / rollback | 高优先 EvolutionRun |
| P2 | 稳定可复现质量/成本/延迟退化 | 通常继续运行或局部降级 | 聚合确认后 Trigger |
| P3 | 新模型、新 Tool、新 Provider、成本/能力机会 | 无紧急动作 | 计划性 Trigger |

P0/P1 可以绕过普通 cooldown/最小样本要求，但不能绕过 EvolutionAuthority、Eval、Budget、Release 或 Governance Kernel。

## 6. Evidence 采集与三层漏斗

模块 11 不直接保存每一条完整 Trace：

```text
L0 Always-on Minimal Evidence
  -> L1 Conditionally Sampled Evidence
  -> L2 On-demand Evidence Expansion
```

### 6.1 L0

所有 Run 形成小型结构化 Summary，主要包含 run/release/agent refs、outcome/duration/retry、model tokens/cost、tool status/outcome certainty、RAG counters/context tokens、security flags、trace/eval/action refs。

不默认包含完整 Prompt、Response、RAG chunks、Tool Payload。

### 6.2 L1

完整 Trace 和详细 Payload 按风险/结果/版本阶段采样：成功低采样、失败较高采样、Canary 提高采样、P0/P1 保留政策允许的必要证据。

### 6.3 L2 Evidence Expansion

只有 Trigger Candidate、Trigger Gate 或 Diagnosis 无法依赖 L0/L1 决定时才启动。推荐：

```text
A current failures
B current successes
C baseline release samples
```

Expansion 必须限制样本数、字节、Token、时间窗和敏感级别。

### 6.4 正常路径 0 LLM Token

默认 Collection、Run Summary、Fingerprint、滚动窗口和 Trigger Candidate 使用规则、计数、SQL/streaming aggregation 和统计；只有 root cause/novelty/value/repair target 无法可靠判断时才升级 Cheap Model / Strong Model。

## 7. Evidence 去重与压缩

错误优先使用确定性 Fingerprint：

```text
release + stage + error_code + tool/model/adapter + operation + normalized signature
```

Projection 只保存 count、affected runs、first/last seen 和少量 sample refs。无法归类的剩余错误才进入 semantic clustering。

```text
Run Summary / Raw refs
  -> exact/fingerprint dedup
  -> rolling statistics
  -> semantic clustering only if needed
  -> signal / opportunity
  -> Trigger Gate
  -> Diagnosis / compact attempt metadata
  -> Active Working Set
```

Pattern、Experience、Lesson、Diagnosis 可以作为内部记录存在，但不成为跨模块 Canonical Object。

## 8. Active Working Set

每次 EvolutionRun 只加载：

- 当前 `EvolutionTrigger`；
- baseline `GenomeManifest`；
- 当前 `mutable_scope`；
- 少量 A/B/C 样本；
- 已执行 mitigation refs；
- 相关成功/失败 Repair attempt refs；
- 必要 Eval/Governance 约束。

必须设置最大 Token、条目数、时间窗/相关性、duplicate/superseded 排除和 Archive/Cold Store 策略。

## 9. Evolution Trigger

### 9.1 两类 Trigger

`reactive`：failure cluster、quality/latency/cost drift、security regression、稳定可复现能力缺陷。

`opportunistic`：新模型、新 Tool/Adapter、新 Provider capability、更低运行成本、新业务目标、scheduled optimization review。

### 9.2 Trigger Gate

```text
signal / opportunity
  -> evidence_sufficient
  -> still_relevant
  -> mutable_surface_match
  -> existing_mitigation_insufficient
  -> novelty_sufficient
  -> expected_value_positive
  -> cooldown_satisfied
  -> EvolutionTrigger
```

Trigger Gate SHOULD 主要使用规则、统计、Projection、索引和确定性查询；只有根因或价值无法可靠分类时才使用模型。

### 9.3 Trigger 不是必须修改

EvolutionRun MAY 以 `no_evolution_needed` 正常结束，例如 Provider 暂态已恢复、用户数据问题、根因不在可修改范围或已有 mitigation 足够。

## 10. Diagnosis 与 Repair Router

问题发生层、root cause 层和 repair target MAY 不同：

```text
observed_problem_scope
  != likely_root_cause_scope
  != repair_target_scope
```

例如 Tool 参数错误可能修 Prompt/Model；RAG empty 可能来自 source/ACL/provider；Workflow 延迟可能来自 Tool/Model。

Repair Router 输出：

```text
NO_EVOLUTION
OPERATIONAL_ONLY
MUTATION R1..R4
ROUTE_GOVERNANCE R5
```

### 10.1 Repair Ladder

| Level | 修复 | 行为 |
|---|---|---|
| R0 | Operational Mitigation | 不改 Genome |
| R1 | Parameter / Config | 产生 Candidate |
| R2 | Component / Routing | 产生 Candidate |
| R3 | Workflow / Composition | 产生 Candidate |
| R4 | Artifact / Code | 产生 Candidate |
| R5 | Governance Boundary | 独立治理，禁止自动自提权 |

### 10.2 Smallest Effective Repair

默认选择能合理解决问题的最小修复范围。修复失败不自动授权扩大 mutable scope；升级到更高层必须有新的诊断/失败证据。

### 10.3 Tool timeout/unknown

```text
timeout
  -> outcome_certainty = unknown
  -> reconciliation first
  -> then diagnose timeout/provider/polling/workflow policy
```

不得机械地把 timeout 上升转换为增加 retry_count。

### 10.4 Governance

ACL、Identity、Permission、PDP/PEP、Secrets、Tool Gateway enforcement、Audit/Eval root、Release Authority、Budget Enforcement、kill switch、legal hold/deletion 属于 R5。

“权限不足导致任务失败”可以修错误 Router/Prompt/Tool choice，但不能自动增加自身权限。

## 11. Candidate Generation

### 11.1 MutationProposal

R1–R4 `MutationProposal` SHOULD 记录：

```yaml
diagnosis_refs: [string]
repair_level: r1 | r2 | r3 | r4
repair_target_scope: [string]
repair_reason_codes: [string]
```

R0/R5 不产生自动 MutationProposal。`repair_target_scope` 必须属于 Authority 与当前 mutable scope 的交集。

### 11.2 Sparse Mutation

默认只修改诊断指向的最小范围。例如 RAG recall 问题优先 Context/Retrieval Policy；无证据不得同时修改 Prompt、Model、Tool 和 Workflow。

### 11.3 GenomeManifest / Candidate

```text
MutationProposal
  -> GenomeManifest candidate
  -> Module 10 ReleaseCandidate
  -> Module 08 Eval
  -> 07/09 gates
  -> ReleaseDecision
```

## 12. Evolution Strategy

V1 MAY 支持 LLM-guided sparse mutation、Genetic/Evolutionary Search、Bayesian Optimization、Self-reflection、Workflow/Tool search、Human-guided。

V1 推荐先实现局部、证据驱动 Strategy；Population Search 属于后续能力。

## 13. Evaluator Funnel

```text
ReleaseCandidate
  -> schema / contract checks
  -> deterministic tests
  -> statistical eval
  -> regression + security hard checks
  -> cheap judge if needed
  -> strong judge if needed
  -> human review if needed
  -> release gates
```

Repair Level SHOULD 调整 Targeted Eval 范围：

- R1：targeted deterministic/statistical + direct regression；
- R2：targeted + compatibility + regression + risk-based Canary；
- R3：workflow/trajectory + regression + latency/cost + Canary；
- R4：unit/integration/security/compatibility/benchmark + full relevant gates。

## 14. 权限

V1 mutable targets 默认：

```text
Observe     allow
Propose     allow
Experiment  allow
Promote     risk-based
```

Prompt/Model Routing/Context/Memory Policy 可按 Gate 自动 Promote；Workflow/Skill 默认 Canary；Tool 默认 Gated；Governance Kernel 永久禁止自动 Propose/Experiment/Promote。

## 15. Budget、Cooldown 与 Evidence Cost

EvolutionRun 使用既有 Budget Domain，限制 model calls、tokens、amount、candidates、attempts、strong model calls、wall time。

Trigger/Evidence Policy SHOULD 同时限制最小演化间隔、新增证据量、trace sample rates、hot storage、semantic clustering jobs、trigger candidates/hour、expansion samples/bytes/tokens。

资源紧张时：

```text
keep Audit / Security / ActionReceipt / P0-P1
  -> keep minimal Run Summary
  -> reduce success full trace
  -> reduce verbose debug
  -> reduce semantic clustering
```

Evidence gap 必须可观测。

EvolutionRun 停止条件包括 target reached、no evolution needed、plateau、budget exhausted、no valid candidate、regression、safety blocked、novelty exhausted、manual stop。

## 16. Lineage、Fitness 与修复经验

V1 保留可追溯性，不新增真相源：

- Lineage：parent_refs + Mutation + ReleaseCandidate + Eval + Release events；
- Fitness：Eval/Cost/SLO comparison view；
- Experience/Lesson：内部记录；
- RunSummary/ErrorFingerprint/AggregateWindow/TriggerCandidate：Projection；
- RepairHistory：Trigger + Diagnosis/attempt metadata + Mutation + Genome + Eval + Release + Production feedback 的 Projection。

相似问题 SHOULD 优先查询已验证成功/失败 Repair path，避免重复推理和实验。

## 17. 三个时间尺度

```text
毫秒~分钟  Operational Response
小时~天    Evolution Response / Repair
周~月      Optimization Review
```

实际时间由风险 Profile、SLO 和任务价值决定。

## 18. Governance Kernel

以下不属于 mutable Genome：Identity/Delegation Root、Permission/PDP/PEP、Tool Gateway enforcement、Secrets、Audit Root、Evaluator Root/Holdout、Release Authority、Budget Enforcement、Deletion/Legal Hold、Kill Switch。

同一递归链不能修改这些能力。

## 19. V2/V3 边界

V2 Planned：Species/Population/Elite、Gene Pool、Capability Transfer、Local+Ecosystem Fitness、Diversity、生态级 Funnel Evaluation。

V3 Research：Meta Evolution、Dynamic Niche/Species、Ecosystem Topology、Pareto Frontier、Evolution Debt/Systemic Risk、ModelEvolutionPort。

V2/V3 不作为 V1 代码和验收要求。

## 20. V1 验收条件

1. P0/P1 可先止血，不等待 EvolutionRun；
2. 普通单次失败不会直接生成 MutationProposal；
3. Trigger Gate 能过滤证据不足、已恢复、不可修改、重复、低价值或 cooldown 问题；
4. 正常 Evidence Collection/Aggregation/Fingerprint/Trigger Candidate 路径为 0 LLM Token；
5. Trigger Engine 不扫描全量 Trace，Evidence Expansion 有明确上限；
6. 基层 RAG/Model/Tool/Workflow/Memory/Runtime 不会因发现问题原地长期自改；
7. Repair Router 能区分 observed symptom、root cause 与 repair target；
8. 默认选择 Smallest Effective Repair，扩大范围必须有新证据；
9. Tool timeout/unknown 先 reconciliation，不机械增加 retry；
10. R5 Governance 问题不能产生自动提升权限的 MutationProposal；
11. R1–R4 Mutation 可追溯 diagnosis refs、repair level 和 target scope；
12. Candidate 复用模块 10/08/07/09 构建、评测和发布；
13. Candidate 无法提升自身 EvolutionAuthority 或修改 Governance Kernel；
14. Active Working Set 不随历史线性增长；
15. 可从当前 Release 追溯到 Trigger、Diagnosis、Mutation、Genome、Eval 和 Evidence refs；
16. V1 未新增 Repair Service/RepairHistory 真相源，也未为 V2/V3 预建独立服务。
