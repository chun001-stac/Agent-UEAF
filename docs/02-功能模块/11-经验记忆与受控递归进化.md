# 11｜经验记忆与受控递归进化

Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 模块定位

本模块是 UEAF V1 的 **Controlled Evolution Kernel**。它把生产运行、评测、成本和业务反馈中的结构化证据转化为有限、可审计、可停止的改进循环。

V1 的目标不是实现完整 Agent 生态，而是先证明：

```text
Evidence / Opportunity
  -> operational response if urgent
  -> Trigger Gate
  -> EvolutionTrigger
  -> bounded EvolutionRun
  -> sparse MutationProposal when justified
  -> GenomeManifest candidate
  -> existing ReleaseCandidate
  -> existing Eval / Release Governance
  -> Production Feedback
```

本模块不是另一个 Agent Runtime，也不是常驻“自我反思 Agent”。没有有效 Trigger 时，不应进行持续演化推理。

Evidence 采集遵循：

> **模块 02–08 产生事实，模块 09 采集/采样/聚合，模块 11 只消费 Projection 与按需引用。**

详细字段和采样规则见 `../01-核心规范/07-V1最小Evidence采集规范.md`。

## 2. V1 一等对象

模块 11 在 V1 只拥有以下演化语义：

- `EvolutionTrigger`；
- `EvolutionRun`；
- `GenomeManifest`；
- `MutationProposal`；
- `EvolutionAuthorityPolicy`。

候选、评测、预算、发布、工件、事故响应和原始 Evidence 不重新定义：

| 能力 | 复用模块 |
|---|---|
| Candidate | 模块 10 `ReleaseCandidate` |
| Eval | 模块 08 `EvalConfig` / `EvalRun` / `EvalResult` |
| Security Gate / immediate security action | 模块 07 |
| Telemetry collection / sampling / aggregation / retention | 模块 09 |
| Operational response / SLO / fallback | 模块 09 |
| Rollback / Release | 模块 08 / 09 既有发布控制 |
| Tool-side containment | 模块 05 Tool Gateway |
| Budget | 既有 Budget Domain / Budget Ledger |
| Artifact / Bundle | 模块 10 / Registry |

模块 11 不拥有第二套 `CandidateRelease`、`EvaluationSuite`、`EvolutionBudget`、`FitnessRecord`、`LineageGraph`、Incident、OperationalResponse、Trace/Metric/Log/Eval/Action 或 Evidence 数据平台真相源。

## 3. 与现有模块的边界

| 模块 | 协作 | 模块 11 不负责 |
|---|---|---|
| 02 Runtime/State | 读取 Run outcome/state summary refs | 不成为 Run State Writer |
| 03 Model | 读取 token/cost/latency/error/invocation refs | 不复制 Prompt/Response 全量历史 |
| 04 Context/RAG/Memory | 读取 retrieval/context summary 与必要 manifest refs | 不拥有业务 `MemoryRecord` 或复制所有 chunks |
| 05 Tool/MCP | 读取 Tool failure/receipt/outcome certainty refs | 不执行事故止血或绕过 Tool Gateway |
| 06 Workflow/Multi-Agent | 读取 fan-out/handoff/node failure summary，可提出 Workflow Mutation | 不修改正在运行的 WorkflowRun |
| 07 Identity/Security | 接收安全事件/mitigation 引用并受安全门禁约束 | 不签发权限，不取代 incident response |
| 08 Eval/Release | 提交 ReleaseCandidate，消费 EvalResult，引用 rollback/release 事实 | 不重建 Eval，不签发 ReleaseManifest |
| 09 Production/Observability | 消费 Run Summary、滚动窗口、Fingerprint、Metric/Cost/SLO/Trace refs | 不再建设并行 collector/store，不把遥测直接当演化结论 |
| 10 Developer/Adapter | 使用 Sandbox/Bundle Builder 构建 Candidate | 不绕过 Developer/Release 流程 |

## 4. 逻辑组件

V1 推荐只保留以下逻辑组件；它们可以在同一进程或模块内实现，不意味着独立服务。

| 组件 | 职责 |
|---|---|
| Evidence Projection Reader | 查询模块 09/08/05 等既有 Projection 与 refs，不复制原始数据 |
| Signal / Opportunity Detector | 从 Run Summary、Metric/Eval/Security/Fingerprint 识别 Trigger Candidate，不创建 Trigger |
| Trigger Gate Engine | 判断证据、相关性、可变范围、现有 mitigation、novelty、expected value、cooldown |
| Evidence Expander | Trigger Gate 信息不足时按引用拉取有界 A/B/C 对照样本 |
| Evolution Coordinator | 形成 `EvolutionTrigger` 后创建并推进 `EvolutionRun` |
| Genome Registry | 保存 `GenomeManifest` 与版本引用 |
| Strategy / Mutation Proposer | 在授权的 mutable scope 内产生有限 `MutationProposal` |
| Working Set Builder | 基于 Trigger + Expansion 结果生成有界演化上下文 |
| Candidate Bridge | 调用模块 10 生成 `ReleaseCandidate` |
| Selection View | 基于模块 08 EvalResult 等证据比较候选，不成为第二真相源 |

V1 不建设独立 Evidence Collector、Evolution Trace Store、GenePool Service、Species Service、Lineage Service 或 Ecosystem Fitness Service。

## 5. 即时运行响应与 Evolution Response

发现问题后，系统 MUST 先判断是否需要即时保护生产，而不是默认启动自我修改。

```text
Observed signal
  ├─ urgent -> Operational Response
  │             rollback / fallback / isolate / degrade / kill
  │
  └─ evidence -> Trigger Gate -> Evolution Response
```

两条链的目标不同：

- Operational Response：解决“现在怎么办”；
- Evolution Response：解决“未来是否值得改变自己”。

模块 11 MUST NOT 为等待 EvolutionRun 而延迟必要的安全隔离、回滚、fallback、降级、限流或 kill switch。

### 5.1 P0-P3

| Priority | 典型场景 | 即时动作 | Evolution |
|---|---|---|---|
| P0 | 数据泄漏、越权、高风险错误动作 | 立即 isolate / rollback / kill | 立即或高优先 Trigger |
| P1 | 大面积质量崩溃、系统性 Tool/Model 失败 | fallback / degrade / rate-limit / rollback | 高优先 EvolutionRun |
| P2 | 稳定可复现的质量/成本/延迟退化 | 通常继续运行或局部降级 | 聚合确认后 Trigger |
| P3 | 新模型、新 Tool、新 Provider、成本/能力机会 | 无紧急动作 | 计划性 Trigger |

P0/P1 可以绕过普通 cooldown/最小样本要求，但不能绕过 EvolutionAuthority、Eval、Budget、Release 或 Governance Kernel。

## 6. Evidence 采集与三层漏斗

模块 11 不直接监听并保存每一条完整 Trace。V1 采用：

```text
L0 Always-on Minimal Evidence
  -> L1 Conditionally Sampled Evidence
  -> L2 On-demand Evidence Expansion
```

### 6.1 L0

所有 Run 形成小型结构化观测/Run Summary，主要包含：

- run/release/agent refs；
- outcome/duration/retry；
- model calls/tokens/cost；
- tool calls/error/outcome certainty；
- RAG counters/context tokens；
- security flags；
- trace/eval/action refs。

不默认包含完整 Prompt、Response、RAG chunks、Tool Payload。

### 6.2 L1

完整 Trace 和详细 Payload 按风险/结果/版本阶段采样：成功低采样、失败较高采样、Canary 提高采样、P0/P1 保留政策允许的必要证据。

### 6.3 L2 Evidence Expansion

只有 Trigger Candidate 或 Trigger Gate 无法依赖 L0/L1 决定时才启动。推荐抽取：

```text
A current failures
B current successes
C baseline release samples
```

Expansion 必须限制样本数、字节、Token、时间窗和敏感级别。

### 6.4 正常路径 0 LLM Token

默认 Collection、Run Summary、Fingerprint、滚动窗口和 Trigger Candidate 使用：

```text
rules / counters / SQL / streaming aggregation / statistics
```

只有根因/novelty/value 无法可靠判断时才升级到 Cheap Model / Strong Model。

## 7. Evidence 去重与压缩

原始证据仍属于原始领域：

- `EvalResult`；
- Trace / Metric / Log；
- `ActionReceipt`；
- Cost / SLO；
- Quality/Security/Operational Gate；
- rollback / fallback / containment 事实引用；
- 明确业务反馈或人工复核。

错误去重优先使用确定性 Fingerprint：

```text
release + stage + error_code + tool/model/adapter + operation + normalized signature
```

内部 Projection 仅保存 count、affected runs、first/last seen 和少量 sample refs。无法归类的剩余错误才进入 semantic clustering。

推荐内部流程：

```text
Run Summary / Raw refs
  -> exact/fingerprint dedup
  -> rolling statistics
  -> semantic clustering only if needed
  -> relevant signal / opportunity
  -> Trigger Gate
  -> compact lesson/attempt metadata
  -> Active Working Set
```

Pattern、Experience、Lesson 可以作为内部记录存在，但 V1 不要求成为跨模块 Canonical Object。

成熟经验 SHOULD 尽量固化为版本化的 Prompt、Policy、Router、Workflow、Tool 或 Skill 工件，而不是永久保留为长文本上下文。

## 8. Active Working Set

每次 EvolutionRun 只加载：

- 当前 `EvolutionTrigger`；
- 当前 baseline `GenomeManifest`；
- 当前 `mutable_scope`；
- 少量直接相关 A/B/C 样本和历史引用；
- 已执行 mitigation 的必要引用；
- 必要 Eval/Governance 约束。

必须设置：

- 最大 Token；
- 最大条目数；
- 最大时间窗或相关性阈值；
- duplicate/superseded 排除；
- Archive/Cold Store 策略。

总历史可增长，但 Active Working Set 不得随历史线性增长。

## 9. Evolution Trigger

### 9.1 两类 Trigger

`reactive`：failure cluster、quality/latency/cost drift、security regression、稳定可复现能力缺陷。

`opportunistic`：新模型、新 Tool/Adapter、新 Provider capability、更低运行成本、新业务目标、scheduled optimization review。

系统没有故障也 MAY 因 opportunity 创建 Trigger。

### 9.2 Trigger Gate

除 P0 快速路径外，默认按以下顺序：

```text
signal / opportunity
  -> evidence_sufficient
  -> still_relevant
  -> mutable_surface_match
  -> existing_mitigation_insufficient
  -> novelty_sufficient
  -> expected_value_positive
  -> cooldown_satisfied
  -> EvolutionTrigger
```

说明：

1. 证据不足：记录信号，继续观察，不创建 Trigger；
2. 问题已消失且复发概率低：不 Trigger；
3. 根因不在 mutable surface：交回对应运行/业务域，不 Trigger；
4. 已有 runbook/fallback 足够：保留证据，不必进化；
5. 环境未变化且同方案已失败：避免重复搜索；
6. 预期收益不足以覆盖成本/回归风险：不 Trigger；
7. 普通问题处于 cooldown：继续聚合；P0/P1 MAY 绕过。

Trigger Gate SHOULD 主要使用规则、统计、Projection、索引和确定性查询；只有根因或价值无法可靠分类时才使用模型。

### 9.3 Trigger 不是“必须修改”

Trigger 只表示“值得启动一次受控分析”。EvolutionRun 分析后 MAY 以 `no_evolution_needed` 正常结束，例如：Provider 暂态已经恢复、用户数据问题、根因不在可修改范围、已有 mitigation 已充分解决。

## 10. Candidate Generation

### 10.1 Sparse Mutation

默认只修改被证据指向的最小范围。例如：

```text
RAG failure
  -> mutable: context/retrieval policy
  -> frozen: permissions / release authority / unrelated tools / unrelated workflow
```

### 10.2 `GenomeManifest`

V1 只维护一个通用 Genome 生命周期：

```text
GenomeManifest<agent>
GenomeManifest<skill>
GenomeManifest<tool>
GenomeManifest<workflow>
GenomeManifest<strategy>
```

不同类型通过 `profile_ref` 定义组件要求，不分别建设五套状态机。

### 10.3 Candidate

Mutation 不直接产生生产版本：

```text
MutationProposal
  -> GenomeManifest candidate
  -> Module 10 ReleaseCandidate
  -> Module 08 Eval
  -> 07/09 gates
  -> ReleaseDecision
```

## 11. Evolution Strategy

V1 可以支持多种 Strategy，但不要求全部实现：

- LLM-guided sparse mutation；
- Genetic/Evolutionary Search；
- Bayesian Optimization；
- Self-reflection；
- Workflow/Tool search；
- Human-guided。

V1 推荐先实现一种局部、证据驱动 Strategy；Population Search 属于后续能力。

## 12. Evaluator Funnel

```text
ReleaseCandidate
  -> schema / contract checks
  -> deterministic tests
  -> statistical eval
  -> regression + security hard checks
  -> cheap judge if needed
  -> strong judge if needed
  -> human review if needed
  -> release gates
```

能够在便宜阶段判定失败的 Candidate 不继续进入昂贵阶段。

V1 不要求每个 Candidate 执行全生态评测。共享资源成本、fan-out、延迟和直接回归只作为模块 08 的现有 Eval 维度。

## 13. 权限

V1 对 mutable targets 默认：

```text
Observe     allow
Propose     allow
Experiment  allow
Promote     risk-based
```

推荐：

- Prompt / Model Routing / Context / Memory Policy：通过独立门禁后可自动 Promote；
- Workflow / Skill：默认 Canary；
- Tool：默认 Gated；
- Governance Kernel：Propose/Experiment/Promote 永久禁止。

企业可通过 `EvolutionAuthorityPolicy` 收紧权限。

## 14. Budget、Cooldown 与 Evidence Cost

`EvolutionRun` 使用既有 Budget Domain 的专用预算切片，至少限制 model calls、input/output tokens、amount、candidates、attempts、strong model calls 和 wall time。

Trigger/Evidence Policy SHOULD 同时限制：

- 同 subject/trigger class 的最小演化间隔；
- 最小新增任务/证据数量；
- success/failure/P0-P1 trace sample rates；
- hot storage / telemetry rate；
- semantic clustering jobs；
- trigger candidates/hour；
- expansion samples/bytes/tokens per trigger。

资源紧张时优先保留：

```text
Audit / Security / ActionReceipt / P0-P1
  -> minimal Run Summary
  -> reduce success full trace
  -> reduce verbose debug
  -> reduce semantic clustering
```

Evidence gap 必须可观测，不能解释为“无异常”。

EvolutionRun 停止条件包括 target reached、no evolution needed、plateau、budget exhausted、no valid candidate、regression、safety blocked、novelty exhausted、manual stop。

生产工作可以持续，但单次 EvolutionRun 必须结束。

## 15. Lineage、Fitness 与经验记录

V1 的原则是“保留可追溯性，不新增真相源”。

- Lineage：通过 `parent_refs`、Mutation、ReleaseCandidate、Eval 和 Release 事件生成 Projection；
- Fitness：通过现有 Eval/Cost/SLO 事实生成比较视图；
- Experience/Lesson：内部结构化记录，不默认进入业务 Agent Memory；
- RunSummary/ErrorFingerprint/AggregateWindow/TriggerCandidate：Projection/内部分析，不是 Canonical Object；
- Gene Pool：V1 只要求 Registry/Artifact 具备未来可复用所需的 provenance 和 compatibility metadata。

## 16. 三个时间尺度

```text
毫秒~分钟
Operational Response
  -> rollback / fallback / isolate / degrade / kill

小时~天
Evolution Response
  -> Trigger / Mutation / Eval / Canary

周~月
Optimization Review
  -> new model / new tool / provider / cost / scheduled opportunity
```

这不是固定 SLA；实际时间由风险 Profile、SLO 和任务价值决定。

## 19. V1 验收条件

V1 至少证明：

1. P0/P1 严重问题可先通过现有安全/运行/发布链止血，不等待 EvolutionRun；
2. 普通单次失败不会直接生成 MutationProposal；
3. Trigger Gate 能阻止证据不足、已恢复、不可修改、重复、低价值或 cooldown 中的问题进入 EvolutionRun；
4. Opportunistic Trigger 可以在系统无故障时评估新模型/Tool/Provider/成本机会；
5. 正常 Evidence Collection、Aggregation、Fingerprint、Trigger Candidate 路径为 0 LLM Token；
6. Trigger Engine 不需要扫描全量 Trace；
7. Full Trace 可按 success/failure/canary/P0-P1 自适应采样；
8. Evidence Expansion 有样本、字节、Token 和敏感级别上限；
9. 模块 11 不复制模块 09/08/05 的原始权威存储；
10. 高基数 ID 不进入常规 Metric label；
11. 一次 EvolutionRun 有明确预算和终态，并可正常结束为 `no_evolution_needed`；
12. 一个局部 Gene 可以产生新 GenomeManifest，而不修改当前 Release；
13. Candidate 复用模块 10/08/07/09 的构建、评测和发布链；
14. Candidate 无法提升自身 EvolutionAuthority 或修改 Governance Kernel；
15. Active Working Set 不随历史线性增长；
16. 可从当前 Release 追溯到 Genome、Mutation、Eval、Trigger Gate 和关键 Evidence refs；
17. V1 未为 Species/GenePool/Meta Evolution 预建独立服务和状态机。
