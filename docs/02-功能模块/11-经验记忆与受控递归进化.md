# 11｜经验记忆与受控递归进化

Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 模块定位

本模块是 UEAF V1 的 **Controlled Evolution Kernel**。它把生产运行、评测、成本和业务反馈中的结构化证据转化为有限、可审计、可停止的改进循环。

V1 的目标不是实现完整 Agent 生态，而是先证明：

```text
Evidence
  -> Trigger
  -> bounded EvolutionRun
  -> sparse MutationProposal
  -> GenomeManifest candidate
  -> existing ReleaseCandidate
  -> existing Eval / Release Governance
  -> Production Feedback
```

本模块不是另一个 Agent Runtime，也不是常驻“自我反思 Agent”。没有有效 Trigger 时，不应进行持续演化推理。

## 2. V1 一等对象

模块 11 在 V1 只拥有以下演化语义：

- `EvolutionTrigger`；
- `EvolutionRun`；
- `GenomeManifest`；
- `MutationProposal`；
- `EvolutionAuthorityPolicy`。

候选、评测、预算、发布和工件不重新定义：

| 能力 | 复用模块 |
|---|---|
| Candidate | 模块 10 `ReleaseCandidate` |
| Eval | 模块 08 `EvalConfig` / `EvalRun` / `EvalResult` |
| Security Gate | 模块 07 |
| Operational Gate | 模块 09 |
| Budget | 既有 Budget Domain / Budget Ledger |
| Release | 模块 08 `ReleaseDecision` / `ReleaseManifest` |
| Artifact / Bundle | 模块 10 / Registry |

模块 11 不拥有第二套 `CandidateRelease`、`EvaluationSuite`、`EvolutionBudget`、`FitnessRecord` 或 `LineageGraph` 真相源。

## 3. 与现有模块的边界

| 模块 | 协作 | 模块 11 不负责 |
|---|---|---|
| 04 Context/RAG/Memory | 读取经治理的必要证据/记忆引用 | 不拥有业务 `MemoryRecord` |
| 06 Workflow/Multi-Agent | 可提出 Workflow 相关 Mutation | 不修改正在运行的 WorkflowRun |
| 07 Identity/Security | 受 PDP、Secret、安全门禁约束 | 不签发权限，不修改 Governance Kernel |
| 08 Eval/Release | 提交 ReleaseCandidate，消费 EvalResult | 不重建 Eval，不签发 ReleaseManifest |
| 09 Production/Observability | 读取 Metric/Cost/SLO/Trace 引用 | 不把遥测直接当演化结论 |
| 10 Developer/Adapter | 使用 Sandbox/Bundle Builder 构建 Candidate | 不绕过 Developer/Release 流程 |

## 4. 逻辑组件

V1 推荐只保留以下逻辑组件；它们可以在同一进程或模块内实现，不意味着独立服务。

| 组件 | 职责 |
|---|---|
| Evidence Aggregator | 聚合最小结构化证据引用 |
| Trigger Engine | 形成 `EvolutionTrigger` |
| Evolution Coordinator | 拥有 `EvolutionRun` 状态机、预算引用和停止条件 |
| Genome Registry | 保存 `GenomeManifest` 与版本引用 |
| Strategy / Mutation Proposer | 产生有限 `MutationProposal` |
| Working Set Builder | 生成有界的演化上下文 |
| Candidate Bridge | 调用模块 10 生成 `ReleaseCandidate` |
| Selection View | 基于模块 08 EvalResult 等证据比较候选，不成为第二真相源 |

V1 不建设独立 GenePool Service、Species Service、Lineage Service 或 Ecosystem Fitness Service。

## 5. Evidence 与经验压缩

原始证据仍属于原始领域：

- `EvalResult`；
- Trace / Metric / Log；
- `ActionReceipt`；
- Cost / SLO；
- Quality/Security/Operational Gate；
- 明确业务反馈或人工复核。

模块 11 只保存必要引用和聚合结果。

推荐内部流程：

```text
Raw refs
  -> exact dedup
  -> statistical / semantic clustering
  -> relevant pattern
  -> compact lesson/attempt metadata
  -> Active Working Set
```

Pattern、Experience、Lesson 可以作为内部记录存在，但 V1 不要求成为跨模块 Canonical Object。

成熟经验 SHOULD 尽量固化为版本化的 Prompt、Policy、Router、Workflow、Tool 或 Skill 工件，而不是永久保留为长文本上下文。

## 6. Active Working Set

每次 EvolutionRun 只加载：

- 当前 Trigger；
- 当前 baseline `GenomeManifest`；
- 当前 `mutable_scope`；
- 少量直接相关的成功/失败历史引用；
- 必要 Eval/Governance 约束。

必须设置：

- 最大 Token；
- 最大条目数；
- 最大时间窗或相关性阈值；
- duplicate/superseded 排除；
- Archive/Cold Store 策略。

总历史可增长，但 Active Working Set 不得随历史线性增长。

## 7. Evolution Trigger

典型触发：

1. 失败率或质量指标越阈；
2. 新的高频 Failure Cluster；
3. Token/费用/延迟显著恶化；
4. 新模型/新工具/新 Provider 能力；
5. 新业务目标；
6. 安全或质量回归；
7. 足够多的新证据；
8. 显式人工或周期复核。

单个失败或普通日常任务不应自动触发演化。

## 8. Candidate Generation

### 8.1 Sparse Mutation

默认只修改被证据指向的最小范围。例如：

```text
RAG failure
  -> mutable: context/retrieval policy
  -> frozen: permissions / release authority / unrelated tools / unrelated workflow
```

### 8.2 `GenomeManifest`

V1 只维护一个通用 Genome 生命周期：

```text
GenomeManifest<agent>
GenomeManifest<skill>
GenomeManifest<tool>
GenomeManifest<workflow>
GenomeManifest<strategy>
```

不同类型通过 `profile_ref` 定义组件要求，不分别建设五套状态机。

### 8.3 Candidate

Mutation 不直接产生生产版本：

```text
MutationProposal
  -> GenomeManifest candidate
  -> Module 10 ReleaseCandidate
  -> Module 08 Eval
  -> 07/09 gates
  -> ReleaseDecision
```

## 9. Evolution Strategy

V1 可以支持多种 Strategy，但不要求全部实现：

- LLM-guided sparse mutation；
- Genetic/Evolutionary Search；
- Bayesian Optimization；
- Self-reflection；
- Workflow/Tool search；
- Human-guided。

V1 推荐先实现一种局部、证据驱动 Strategy；Population Search 属于后续能力。

## 10. Evaluator Funnel

```text
ReleaseCandidate
  -> schema / contract checks
  -> deterministic tests
  -> statistical eval
  -> regression + security hard checks
  -> cheap judge if needed
  -> strong judge if needed
  -> human review if needed
  -> release gates
```

能够在便宜阶段判定失败的 Candidate 不继续进入昂贵阶段。

V1 不要求每个 Candidate 执行全生态评测。共享资源成本、fan-out、延迟和直接回归只作为模块 08 的现有 Eval 维度。

## 11. 权限

V1 对 mutable targets 默认：

```text
Observe     allow
Propose     allow
Experiment  allow
Promote     risk-based
```

推荐：

- Prompt / Model Routing / Context / Memory Policy：通过独立门禁后可自动 Promote；
- Workflow / Skill：默认 Canary；
- Tool：默认 Gated；
- Governance Kernel：Propose/Experiment/Promote 永久禁止。

企业可通过 `EvolutionAuthorityPolicy` 收紧权限。

## 12. Budget 与停止

`EvolutionRun` 使用既有 Budget Domain 的专用预算切片，至少限制：

- model calls；
- input/output tokens；
- amount；
- candidates；
- generations/attempts；
- strong model calls；
- wall time。

停止条件包括：

- target reached；
- plateau；
- budget exhausted；
- no valid candidate；
- regression；
- safety blocked；
- novelty exhausted；
- manual stop。

生产工作可以持续，但单次 EvolutionRun 必须结束。

## 13. Lineage、Fitness 与经验记录

V1 的原则是“保留可追溯性，不新增真相源”。

- Lineage：通过 `parent_refs`、Mutation、ReleaseCandidate、Eval 和 Release 事件生成 Projection；
- Fitness：通过现有 Eval/Cost/SLO 事实生成比较视图；
- Experience/Lesson：内部结构化记录，不默认进入业务 Agent Memory；
- Gene Pool：V1 只要求 Registry/Artifact 具备未来可复用所需的 provenance 和 compatibility metadata。

## 14. Governance Kernel

以下能力不属于 mutable Genome：

```text
Identity / Delegation Root
Permission / PDP / PEP
Tool Gateway enforcement
Secrets
Audit Root
Evaluator Root / Holdout
Release Authority
Budget Enforcement
Deletion / Legal Hold
Kill Switch
```

同一递归链不能修改这些能力。

## 15. V2/V3 边界

### V2 Planned

- Species / Population / Elite；
- Gene Pool 正式领域；
- Capability Transfer；
- Local + Ecosystem Fitness；
- Diversity / Monoculture Risk；
- 生态级 Funnel Evaluation。

### V3 Research

- Meta Evolution；
- Dynamic Niche / Species；
- Ecosystem Topology Evolution；
- Pareto Frontier；
- Evolution Debt / Systemic Risk；
- ModelEvolutionPort。

V2/V3 可以继续完善文档，但不得作为 V1 代码和验收范围。

## 16. V1 验收条件

V1 至少证明：

1. 无 Trigger 时不会对每个生产任务追加演化模型调用；
2. 一次 EvolutionRun 有明确预算和终态；
3. 一个局部 Gene 可以产生新 GenomeManifest，而不修改当前 Release；
4. Candidate 复用模块 10/08/07/09 的构建、评测和发布链；
5. Candidate 无法提升自身 EvolutionAuthority 或修改 Governance Kernel；
6. Active Working Set 不随历史线性增长；
7. 可从当前 Release 追溯到 Genome、Mutation 和 Eval 证据；
8. V1 未为 Species/GenePool/Meta Evolution 预建独立服务和状态机。
