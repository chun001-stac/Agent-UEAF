# UEAF 端到端时序

## 1. 目的与适用范围

本文给出 UEAF 从请求进入、准入、上下文构建、模型推理、工具副作用、暂停恢复到终态提交的可实施时序。它约束跨模块调用顺序、事务边界、幂等键、失败处理和证据落点；具体框架的内部 Agent Loop 由 Runtime Adapter 实现，但不得改变本时序的企业控制点。

规范对象统一使用 TaskState、RunRecord、RunAdmissionResult 和 ActionRecord。TaskState 表示任务的确定性进度，RunRecord 表示一次运行；两者不得被框架原生 Session、Thread、Run 或 State 替代。

## 2. 参与者与职责

| 参与者 | 职责 | 不得承担 |
|---|---|---|
| Channel / Client | 提交请求、接收流式事件或异步结果 | 伪造主体、租户和发布版本 |
| Agent Gateway | 协议归一、边缘预校验、认证接入、幂等入口、响应封装 | 生成 RunAdmissionResult、推进 RunPhase、直接调用模型或企业工具 |
| Admission Coordinator | 针对已创建的 run_id 组合发布、策略、配额、预算、区域、能力与依赖检查 | 在没有 run_id 时准入、创建新的模糊发布门对象 |
| Task/Run State Service | 原子创建和推进 TaskState、RunRecord、事件与租约 | 执行业务副作用 |
| Run Coordinator | 驱动规范状态机、调度 Runtime Adapter、处理暂停恢复和终态 | 绕过 Gateway 访问模型、知识或工具 |
| Context Builder | 在预算和数据策略内生成 ContextManifest | 把检索结果直接写成业务事实 |
| Prompt/Model Gateway | 固定 PromptContract、ModelRoute、预算和结构化输出验证 | 自行决定工具授权 |
| Runtime Adapter | 桥接 LangGraph、MAF、OpenAI Agents SDK、Google ADK、CrewAI 等运行机制 | 成为 Task/Run 真相源 |
| Tool Gateway | ToolIntent 校验、PolicyDecision、审批、ActionRecord、凭据、执行和对账 | 把发现、连接或 MCP 能力视为授权 |
| Evidence/Audit | 记录不可抵赖审计、Trace、Eval 引用和收据 | 反向改变业务状态 |

## 3. 正常主流程

~~~mermaid
sequenceDiagram
    autonumber
    participant C as Client
    participant G as Agent Gateway
    participant A as Admission Coordinator
    participant I as 02 Runtime Ingress
    participant S as Task/Run State Service
    participant R as Run Coordinator
    participant X as Context Builder
    participant D as Runtime Adapter
    participant M as Prompt/Model Facade
    participant P as Model Provider
    participant T as Tool Gateway
    participant E as Evidence/Audit

    C->>G: RequestEnvelope + idempotency_key
    G->>G: 协议校验、认证、租户解析
    G->>G: 边缘预校验、认证、租户绑定、重放防护
    alt edge rejected
        G->>E: ueaf.request.rejected
        G-->>C: 确定性拒绝 + reason_code
    else edge accepted
        G->>E: ueaf.request.accepted
        G->>I: accepted candidate + TaskEnvelope + idempotency_key
        I->>S: createOrReuse(TaskState, RunRecord(queued))
        S-->>I: task_id + run_id + revision
        I-->>G: queued response
        G-->>C: accepted/queued + run_id
        S-->>R: RunQueued event
        R->>S: acquireAdmissionLease + queued to admitting
        R->>A: AdmitRun(run_id, expected_revision)
        A->>A: Release/Capability/Policy/Quota/Budget/Region/Health
        A-->>R: RunAdmissionResult
        alt run rejected
            R->>S: terminal + rejected
        else run deferred
            R->>S: waiting + condition_refs
        else run admitted
            R->>S: admitting to running + execution lease
            R->>R: 02 校验 RuntimeStartCommand 绑定 admitted RunAdmissionResult，并映射 SPI 请求
            R->>D: StartRun(RuntimeStartRequest)
            D-->>R: RuntimeSession
            D->>X: ContextBuildPort(run_id, policy, budget)
            X-->>D: ContextManifest + EvidencePack refs
            D->>M: ModelStepPort request + prompt/context refs
            M->>M: 03 绑定 PromptContract、ContextManifest、ModelRoute
            M->>P: ModelInvocation
            P-->>M: ModelRunResult / stream
            M->>M: 03 执行结构、证据与语义校验
            M-->>D: StructuredDecision + usage
            alt tool intent
                D-->>R: ToolIntent
                R->>T: authorizeAndExecute(ToolIntent)
                T->>T: PolicyDecision / Approval / ActionRecord
                T-->>R: ToolResult + action_ref or Interruption
                R->>D: resume(tool result)
            else final candidate
                D-->>R: CompletionCandidate
            end
            R->>S: commit terminal RunRecord + result_ref + TaskState revision + outbox
            S->>E: publish committed outbox events
            R-->>G: ResultEnvelope
            G-->>C: result or completion notification
        end
    end
~~~

### 3.1 入口幂等

Gateway 只验证并传递 idempotency_key，不创建 Task/Run。模块 02 Runtime Ingress/State Service 以 tenant_id、channel_id、idempotency_key 构成入口幂等范围：相同范围和相同请求摘要返回已有 task_id/run_id；相同键但摘要不同返回 idempotency_conflict。边缘预校验通过后，幂等记录、TaskState 初始版本、RunRecord(phase=queued) 和首个 outbox 事件必须处于同一事务。边缘预校验失败时不得创建 RunRecord。

### 3.2 准入顺序

UEAF 必须区分边缘预校验和 Run 准入。边缘预校验在尚无 run_id 时依次执行：

1. 请求 Schema、大小、媒体类型和时间窗；
2. PrincipalContext 的签名、租户、委托链和会话约束；
3. 租户绑定、重放防护和最低安全检查。

边缘预校验只产生 ueaf.request.accepted 或 ueaf.request.rejected，不产生 RunAdmissionResult。accepted 后 Runtime Domain 创建 TaskState 和 RunRecord(phase=queued)，冻结 release_id、runtime_adapter_ref、任务引用和初始预算引用。Run Coordinator 获得 admission lease 并提交 queued → admitting 后，Admission Coordinator 针对该 run_id 依次校验：

1. AgentDefinition 与 ReleaseManifest 的签名、生命周期、环境和兼容性；
2. 输入数据分类、用途、区域和 TenantProfile；
3. 配额、并发、预算、截止时间和风险；
4. Runtime Adapter 必需能力和依赖健康度；
5. 入口 PolicyDecision 及其他运行条件。

RunAdmissionResult 必须包含 run_id，只表达 admitted、rejected 或 deferred，并携带 reason_codes、expires_at、依赖摘要和证据引用。admitted 原子提交 admitting → running；rejected 原子提交 terminal/rejected；deferred 提交 admitting → waiting，并带可重试时间或等待条件。

### 3.3 状态创建与租约

Run Coordinator 只有持有未过期租约及当前 fencing_token 才能推进 RunRecord。所有写入使用 expected_revision；版本冲突后必须重新读取，禁止覆盖写。租约到期只表示协调权失效，不代表运行失败，也不能推断在途工具动作失败。

## 4. 工具动作与副作用时序

~~~mermaid
sequenceDiagram
    autonumber
    participant R as Run Coordinator
    participant T as Tool Gateway
    participant P as Policy/Approval
    participant L as Action Store
    participant V as Credential Broker
    participant B as Business System
    participant E as Audit/Outbox

    R->>T: ToolIntent + run revision
    T->>T: 服务端绑定并规范化；计算稳定 action_fingerprint + action_key
    T->>L: createOrResume ActionRecord(proposed, action_key, action_fingerprint)
    L-->>T: action_id + revision
    T->>L: CAS proposed to validating
    T->>T: Schema、租户、用途、风险、资源、能力与预算校验
    alt validation failed
        T->>L: CAS validating to terminal/invalid
        L->>E: invalid action event via outbox
        T-->>R: invalid + evidence_ref
    else validation passed
        T->>L: CAS validating to authorizing
        T->>P: authorize(action_fingerprint, PrincipalContext)
        P-->>T: PolicyDecision
        alt outcome=deny
            T->>L: CAS authorizing to terminal/denied
            L->>E: denied action event via outbox
            T-->>R: denied + evidence_ref
        else outcome=require_approval
            T->>P: create ApprovalRequest(action_fingerprint)
            P-->>T: approval_request_id + status=pending
            T->>L: CAS authorizing to waiting_approval + approval_request_ref
            T-->>R: Interruption(approval) + approval_request_id
        else outcome=allow
            T->>L: reserve existing action_key + fingerprint; CAS authorizing to reserved
            L-->>T: action_id + reservation_ref
            T->>L: acquire execution lease + fencing_token
            L-->>T: fencing_token
            T->>V: issue scoped short-lived credential
            V-->>T: credential handle
            T->>L: mark executing + attempt
            T->>B: execute(command, downstream_idempotency_key)
            alt confirmed response
                B-->>T: business receipt
                T->>L: commit terminal/executed or terminal/failed + ActionReceipt
            else timeout or connection loss
                T->>L: mark reconciling + unknown ActionReceipt
                T->>B: query by idempotency key/business key
                B-->>T: authoritative status
                T->>L: commit reconciled result + receipt
            end
            L->>E: action events via outbox
            T-->>R: ActionReceipt
        end
    end
~~~

ActionRecord 的 action_key 必须在 tenant_id、tool_id、operation、normalized_input_hash、business_scope 范围内稳定。一个 ActionRecord 可有多个 ExecutionAttempt，但只有一条受控结果序列。超时、断连或 Adapter 崩溃导致结果未知时必须进入 unknown/reconciling；禁止直接重试非幂等写操作。

审批决定绑定 action_fingerprint、policy_version、approver、scope 和 expires_at。`require_approval` 只能进入 `waiting_approval`；拒绝或过期提交 `terminal/approval_rejected`，取消提交 `terminal/cancelled`。审批通过后必须回到 `authorizing`，以当前上下文重新求值；只有新的 `PolicyDecision.outcome=allow` 才能使用记录中既有的 action_key 与 action_fingerprint 预留并进入 `reserved`。输入、工具版本、主体、用途或风险变化后，旧审批失效并重新授权。

## 5. 暂停、恢复与人工介入

~~~mermaid
sequenceDiagram
    participant R as Run Coordinator
    participant S as State Service
    participant H as Human Task Service
    participant D as Runtime Adapter

    R->>S: RegisterWait(reason, condition_refs, checkpoint)
    S-->>R: RunRecord(waiting) + revision
    S->>H: HumanTask/ApprovalRequest event
    H-->>S: ResumeSignal + actor + evidence
    S->>S: 去重、校验条件、原子登记信号
    S-->>R: RunResumable event
    R->>S: acquireLease + expected_revision
    R->>D: ResumeRun(RuntimeResumeRequest)
    D-->>R: RuntimeSession（沿用既有 session identity）
~~~

等待状态必须包含 WaitReason、condition_refs、超时策略和可用 Checkpoint。恢复信号以 resume_signal_id 去重，并校验 tenant_id、run_id、等待条件、主体权限和有效期。恢复不得静默更换 ReleaseManifest 或 Runtime Adapter；确需迁移时必须走显式迁移流程并记录前后摘要。

## 6. 取消、超时与级联传播

1. 客户端取消先记录 CancelRequested，再通知 Run Coordinator 和 Runtime Adapter。
2. Coordinator 停止发起新的模型或工具动作，并尝试取消可取消的在途调用。
3. 已提交的外部副作用不得因 Run 取消而标记为撤销；若业务支持补偿，创建新的受控补偿 ActionRecord。
4. 在途动作状态未知时，Run 可进入 waiting/reconciling，直到取得权威结果或人工裁决。
5. 截止时间到达使用同一取消协议，但 reason_code 为 deadline_exceeded。
6. Run 终态必须独立记录 RunPhase=terminal 与 CompletionDisposition，取消、失败、部分完成、拒绝和成功不得混用。

## 7. 事件与一致性要求

| 边界 | 一致性 | 实现要求 |
|---|---|---|
| TaskState、RunRecord、入口幂等、首事件 | 强一致 | 单库事务或等价原子协议 |
| RunRecord 状态推进与 outbox | 强一致 | 同一事务写状态和待投递事件 |
| ActionRecord 预占与 action_key | 强一致 | 唯一约束、CAS、fencing |
| 业务系统写入 | 依赖下游 | 下游幂等键、收据、查询/对账 |
| Trace、搜索、指标、控制台投影 | 最终一致 | 可重放消费、租户过滤、延迟 SLO |
| Eval 与证据图 | 有界最终一致 | 决策前验证所需引用闭合 |

EventEnvelope 至少携带 event_id、event_name、event_version、tenant_id、aggregate_type、aggregate_id、aggregate_revision、sequence、occurred_at、recorded_at、producer、correlation_id、causation_id、trace_id、release_id、payload_schema_ref 和 integrity_ref。消费者按 event_id 去重，按聚合版本检测缺口，不依赖全局顺序。

## 8. 失败矩阵

| 失败点 | 状态处理 | 自动动作 | 禁止行为 |
|---|---|---|---|
| 认证或契约失败 | 不创建 Run 或返回已存在结果 | 写安全审计 | 模糊映射到系统错误 |
| 准入依赖短暂不可用 | RunAdmissionResult=deferred | 有界退避 | 未验证即放行 |
| State Service 事务冲突 | 保持原 revision | 重读后重算 | last-write-wins |
| Runtime Adapter 崩溃 | Run 保持可恢复 | 租约到期后从 Checkpoint 恢复 | 以内存状态为准 |
| 模型限流 | RunPhase=waiting 或 retrying | 预算内退避/换允许路由 | 绕过 ModelRoute |
| 工具结果未知 | ActionRecord=reconciling | 查询、回调或人工对账 | 盲目再次写入 |
| outbox 投递失败 | 业务事务仍有效 | 重投并去重 | 回滚已提交外部副作用 |
| 审计不可用 | 高风险动作 fail closed | 缓冲受控低风险事件 | 丢弃不可审计动作 |

## 9. 验收场景

1. 同一 idempotency_key 并发提交 100 次，只产生一个 TaskState 和一个初始 RunRecord。
2. Coordinator 在模型结果落地前后分别崩溃，恢复后状态无覆盖、模型预算不被无限重复消耗。
3. 写工具响应超时但下游已成功，系统通过对账把同一 ActionRecord 收敛为 succeeded，且不重复写。
4. 等待审批的 Run 在 24 小时后由合法主体恢复，仍绑定原 release_id；过期审批无法恢复。
5. 过期 fencing_token 的 Coordinator 无法推进 RunRecord 或 ActionRecord。
6. 取消传播不会把已完成副作用伪装为已撤销。
7. 每个结果均可从 task_id/run_id 追溯到主体、发布版本、上下文来源、模型用量、PolicyDecision、ActionReceipt 和审计事件。
