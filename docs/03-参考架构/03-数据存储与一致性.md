# UEAF 数据存储与一致性

## 1. 设计原则

UEAF 将“语义所有权”“状态写入者”“物理存储”和“查询投影”分离。数据库类型可以替换，但每个规范对象的唯一语义所有者不能变化：

| 规范对象 | 语义所有者 | 唯一写入者 | 权威存储 |
|---|---|---|---|
| TaskState | Task Domain | Task State Service | Transaction Store / Event Store |
| RunRecord | Runtime Domain | Run Coordinator 经 State Service | Transaction Store / Event Store |
| RunAdmissionResult | Admission Domain | Admission Coordinator | Transaction Store + Evidence reference |
| ContextManifest | Context Domain | Context Builder | Metadata Store |
| ActionRecord | Tool/Action Domain | Action Coordinator / Reconciler | Action Store |
| PolicyDecision | Security Policy Domain | PDP | Decision Store |
| MemoryRecord | Memory Domain | Memory Service | Memory Store |
| ReleaseDecision | Release Governance | Release Governance | Decision Store / Immutable Registry |
| ReleaseManifest | Release Control | Manifest Signer / Release Controller | Release Registry / Immutable Registry |
| BusinessFact | 企业业务域 | 对应 System of Record | 业务系统 |

日志、Trace、搜索索引、向量索引、缓存和控制台视图都不是权威状态。它们可以重建，不得反向覆盖 TaskState、RunRecord 或 ActionRecord。

## 3. 推荐物理存储

| 数据类型 | 90 天 MVP | 扩展方案 | 关键约束 |
|---|---|---|---|
| TaskState、RunRecord、RunAdmissionResult、租约、幂等、outbox | PostgreSQL | 按 tenant/cell 分片的关系库或分布式 SQL | 事务、唯一约束、CAS、RLS |
| ActionRecord、ExecutionAttempt、ActionReceipt | PostgreSQL 独立 Schema/库 | 高隔离 Action Store | action_key 唯一、fencing、不可覆盖历史 |
| 大型输入、结果、Checkpoint、EvidencePack | S3 兼容对象存储 | 区域化对象存储 | 内容摘要、加密、保留、对象锁 |
| 事件传输 | Kafka / 云消息服务 | 分区事件平台 | 至少一次、按聚合分区、DLQ |
| 热缓存、速率和短租约辅助 | Redis | 区域缓存集群 | 不作为权威；可全量丢失恢复 |
| 文档检索与向量 | OpenSearch/向量数据库 | 多索引/专属集群 | 租户、分类、用途、ACL 过滤 |
| MemoryRecord | PostgreSQL + 对象/向量引用 | 专用 Memory Store | 写入治理、来源、TTL、删除传播 |
| AuditEvent | WORM 对象/日志存储 | 合规归档平台 | 不可抽样、链式完整性、法定保留 |
| Trace/Metric/Log | OpenTelemetry 后端 | 分层遥测平台 | 与 Audit/Eval 分离、脱敏采样 |
| Registry | 关系元数据 + 内容寻址工件库 | 多区域只读复制 | 版本不可变、签名、摘要 |

选择产品时优先验证事务、租户隔离、区域驻留、备份恢复和删除证明，不以“原生 AI”标签替代一致性要求。

## 4. 核心表与键设计

### 4.1 Task 与 Run

| 表 | 主键/唯一键 | 关键字段 |
|---|---|---|
| task_state | tenant_id + task_id | phase/progress、confirmed_facts_ref、open_conditions、revision、created_at、updated_at |
| run_record | tenant_id + run_id | task_id、phase、completion_disposition、release_id、runtime_adapter_ref、budget_snapshot、revision、sequence、lease、checkpoint_ref |
| run_admission_result | tenant_id + run_admission_result_id | run_id、outcome、validation_refs、policy_decision_refs、budget_snapshot_ref、release_manifest_ref、reason_codes |
| request_idempotency | tenant_id + channel_id + idempotency_key | request_hash、task_id、run_id、response_ref、expires_at |
| run_event | tenant_id + run_id + sequence | event_id、revision、event_name/version、payload_ref、correlation/causation、integrity_ref |
| outbox | outbox_id | aggregate_type/id/revision、event_id、payload_ref、published_at、attempt |

约束：

- run_record 的 tenant_id、task_id 必须外键关联同租户 task_state；
- phase 非 terminal 时 completion_disposition 必须为空，terminal 时必须非空；
- 一个 run_admission_result 必须引用已存在的 run_id；
- run_id 创建时冻结 release_id 与 runtime_adapter_ref；
- run_event 的 run_id + sequence 和 event_id 均唯一；
- 所有更新包含 WHERE revision = expected_revision，并原子 revision + 1。

### 4.2 动作账本

| 表 | 主键/唯一键 | 关键字段 |
|---|---|---|
| action_record | tenant_id + action_id | run_id、tool_id/version、operation、action_key、phase、intent_hash、policy_ref、approval_ref、revision |
| execution_attempt | tenant_id + action_id + attempt_no | fencing_token、credential_ref、started_at、ended_at、transport_status、provider_request_ref |
| action_receipt | tenant_id + receipt_id | action_id、outcome、business_ref、provider_evidence_ref、integrity_ref |
| reconciliation_case | tenant_id + case_id | action_id、reason、query_strategy、status、owner、evidence_refs |

tenant_id + action_key 必须唯一。ActionRecord 状态和同事务 outbox 一起提交；ExecutionAttempt 只能追加，不能覆盖先前超时。ActionReceipt 不保存长期凭据或不必要业务正文，只保存最小结果与受控引用。

### 4.3 对象键

对象路径采用 region/environment/tenant_id/object_type/object_id/content_digest；安全授权依赖对象元数据和 IAM 条件，不只依赖路径字符串。每个对象至少具有 tenant_id、classification、purpose、owner_domain、schema_ref、content_digest、encryption_key_ref、retention_policy_ref 和 legal_hold。

## 5. 事务边界

### 5.1 必须原子的边界

1. 边缘预校验通过后：入口幂等记录 + TaskState 初始版本 + RunRecord(queued) + 首个 run_event + outbox；
2. Run 状态推进：RunRecord CAS + run_event + outbox；
3. Run 准入：RunAdmissionResult + RunRecord 的 admitting 出口 + 事件；
4. Task 确认事实更新：TaskState CAS + 来源引用 + 事件；
5. 动作预占：ActionRecord + action_key 唯一约束 + 事件；
6. 动作结果：ActionRecord 推进 + ExecutionAttempt/ActionReceipt + outbox；
7. 终态提交：结果引用 + RunRecord(terminal/disposition) + 完成条件快照 + outbox。

上述边界优先在一个数据库事务完成。若物理拆库，必须使用明确的 saga/命令确认协议，且在未确认时保持 waiting/unknown，不用分布式事务假象掩盖不确定性。

### 5.2 不要求全局事务的边界

- 事务库到事件总线通过 transactional outbox；
- 对象上传采用“先暂存、校验摘要、事务登记引用、后清理孤儿”；
- 搜索、向量、Trace、Metric、Log 和控制台投影最终一致；
- 企业业务系统写入依靠 action_key、下游幂等、业务收据和对账；
- Registry 多区域复制最终一致，但生产准入只读取已验证的本地不可变摘要。

## 6. 两级接入与准入的数据顺序

1. 边缘预校验阶段没有 run_id，不写 RunAdmissionResult。
2. 预校验失败只写 ueaf.request.rejected、安全审计和必要幂等拒绝信息，不创建 RunRecord。
3. 预校验成功形成不可变 TaskEnvelope，创建 TaskState 和 RunRecord(queued)。
4. Run Coordinator 获得 admission lease，CAS 为 admitting。
5. Admission Coordinator 针对 run_id 写 RunAdmissionResult。
6. admitted、deferred、rejected 分别与 running、waiting、terminal/rejected 原子绑定。

数据库约束应拒绝没有 run_id 的 RunAdmissionResult，并通过状态迁移检查拒绝从 queued 直接进入 running。

## 7. 投递、排序和去重

事件总线采用至少一次投递。生产者事务提交后由 outbox relay 发布；消费者按 event_id 去重，按 aggregate_type + aggregate_id 分区并用 sequence 检测缺口。

| 场景 | 去重键 | 冲突处理 |
|---|---|---|
| 外部请求 | tenant/channel/idempotency_key | 同键同摘要返回已有结果；异摘要拒绝 |
| Run 命令 | command_id + expected_revision | 重复返回已提交版本；过期版本冲突 |
| 领域事件 | event_id | 已消费则 ACK；序号缺口暂停投影并补拉 |
| 工具动作 | tenant_id + action_key | 返回已有 ActionRecord，不重新执行 |
| 恢复信号 | tenant_id + resume_signal_id | 已处理则返回当前 RunRecord |
| 回调通知 | delivery_id | 可重投；接收方确认后标记 |

不得承诺端到端 exactly-once。UEAF 的目标是：至少一次消息 + 权威状态 CAS + 副作用幂等/fencing/收据/对账，从而实现可证明的 effectively-once 业务效果。

## 8. 缓存和查询投影

缓存键必须包含 tenant_id、environment、object type、object id 和 canonical version。以下内容不得只存在缓存：租约 fencing 单调序列、RunRecord、ActionRecord、审批、预算账本、发布生命周期和审计。

缓存失效采用版本化读取：调用方携带已知 revision；缓存对象的 revision 低于权威版本时必须回源。权限与策略缓存不得超过 PolicyDecision 有效期；撤销事件优先级高于普通投影，并具有最大传播 SLO。

控制台查询使用 CQRS 投影，但每个页面显示 projection_as_of、source_revision 和 freshness。执行控制命令前重新读取权威对象，不以列表页状态作为前置条件。

## 9. 检索、记忆与业务事实

- 原始语料和业务事实引用是权威；向量是可重建索引；
- ContextManifest 冻结一次模型调用实际采用的来源、版本、排序、过滤和 token 分配；
- MemoryCandidate 经治理后才能写成 MemoryRecord，模型输出不能直接写长期记忆；
- 删除请求先标记权威记录，再传播至对象、索引、缓存、备份策略和模型供应商状态；
- BusinessFactRef 只指向业务系统事实，不复制为 UEAF 可随意修改的字段；
- 检索查询必须同时应用 tenant、ACL、classification、purpose、region 和时间有效性。

## 10. 加密、保留与删除

传输使用双向 TLS 或等价机制；静态数据按环境和租户等级使用独立 KMS key。敏感字段采用应用层信封加密，密钥引用与密文分离。凭据只以短时句柄存在，不进入 EventEnvelope、Trace 或 Checkpoint。

| 数据 | 默认保留建议 | 删除要求 |
|---|---:|---|
| Request/Result 正文 | 30–90 天，按分类调整 | 删除对象并保留最小审计摘要 |
| TaskState/RunRecord | 1 年或业务策略 | 归档后按法规删除/匿名化 |
| ActionRecord/Receipt | 1–7 年 | 与业务和审计策略一致 |
| AuditEvent | 按法规，通常 3–7 年 | WORM 到期或合法保留 |
| Trace/Log | 7–30 天 | 自动 TTL、正文脱敏 |
| MemoryRecord | 明确 TTL 或用途期限 | 删除传播和完成证明 |
| Eval 数据 | 候选生命周期 + 回归周期 | 数据集版本与主体请求联动 |

legal hold 优先于普通 TTL，但必须有范围、签发者、原因和到期复核。删除作业输出 DeletionReceipt，记录所有受影响存储、供应商状态和未完成例外。

## 11. 备份、恢复与迁移

事务库执行持续日志归档和每日全量备份；Action Store、Registry 和 Audit 使用独立备份策略。每季度至少做一次隔离环境恢复演练，验证：

1. tenant_id/RLS/密钥关系仍正确；
2. TaskState、RunRecord、RunAdmissionResult、ActionRecord 修订连续；
3. outbox 可从恢复点重投而不重复业务副作用；
4. unknown 动作进入对账而不是被标记失败；
5. 对象摘要、事件链和审计完整性通过；
6. 搜索与向量可由权威来源重建。

Schema 迁移采用 expand → dual-read/write（必要时）→ backfill → verify → contract。破坏状态语义、枚举、action_key 或 Checkpoint 的变更必须提高契约版本并重新评测；长运行继续绑定旧 Adapter/Schema，或通过显式迁移和验证切换。

## 12. 数据一致性验收

1. 100 个并发相同请求仅产生一个 queued Run；每个 RunAdmissionResult 都有已存在的 run_id。
2. queued 不能绕过 admitting 进入 running；admitting 的三个出口与准入结果处于同一事务。
3. 模拟 outbox 重投和消费者崩溃，投影最终一致且外部副作用不重复。
4. 模拟工具响应丢失，ActionRecord 保持 unknown/reconciling，并通过权威查询收敛。
5. 模拟缓存全部丢失，Task/Run/Action/审批/发布状态无数据损失。
6. 恢复备份后，跨表 revision、事件 sequence、对象摘要和审计链可验证。
7. 两个租户无法借助 SQL、对象、向量、缓存、批处理、备份恢复或遥测查询互访。
8. Memory 与数据删除能传播到所有投影和供应商状态，并输出可审计删除证明。
