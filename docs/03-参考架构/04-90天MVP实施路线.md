# UEAF 90 天 MVP 实施路线

## 1. MVP 目标

90 天内交付一个可在单区域生产环境运行的 UEAF Enterprise Profile 最小闭环：一个真实业务 Agent 可从统一入口进入，经过边缘预校验、queued Run 创建和针对 run_id 的正式准入，通过可替换 Runtime Adapter 执行，所有模型和工具访问经过 UEAF Gateway，写动作具有 PolicyDecision、审批、ActionRecord、收据和对账，最终可以审计、评测、灰度和回滚。

**V1 MVP 同时必须证明 Controlled Evolution Kernel 的最小纵向闭环，而不是只完成 Runtime + Governance 底座。** 90 天内至少选定一个真实或可控注入的退化场景（优先 RAG retrieval/context、Model schema/token/route 或 Tool timeout/rate-limit），完成：

```text
Observed degradation / opportunity
  -> L0/L1 Evidence
  -> Trigger Candidate
  -> Trigger Gate
  -> EvolutionTrigger
  -> bounded EvolutionRun
  -> Diagnosis / Repair Router
  -> R1/R2 MutationProposal
  -> GenomeManifest candidate
  -> ReleaseCandidate
  -> Eval / Gates
  -> Accept / Reject
  -> if accepted: Canary / Production feedback
```

MVP 的成功不是“完成一个聊天演示”，而是以下业务与演化闭环可重复运行：

1. 选择一个边界清晰、价值可衡量、最多两个写操作的业务场景；
2. 接入企业 IdP、一个知识源、一个模型供应商和一个业务系统；
3. 支持同步或异步请求、暂停审批、恢复和确定终态；
4. 以 LangGraph 为首个 Runtime Adapter，再以第二个只读 Adapter 证明 UEAF 契约没有绑定单一框架；
5. 使用质量、安全、生产就绪和发布四类独立决定完成生产灰度；
6. 从真实生产/预生产 Evidence 中至少完成一次 Single-Candidate Evolution，并用既有 Eval/Release 证明候选相对 baseline 是否更好。

## 2. 范围与约束

### 2.1 必须在 90 天内交付

- 统一 Schema：PrincipalContext、RequestEnvelope、TaskEnvelope、TaskState、RunRecord、RunAdmissionResult、ContextManifest、ToolIntent、PolicyDecision、ActionRecord、ActionReceipt、EvalResult、ReleaseManifest；
- 两级接入生命周期：边缘预校验 → queued Run → admitting → admitted/deferred/rejected；
- RunPhase 与 CompletionDisposition 分离的持久状态机；
- Context Builder、PromptContract、Model Gateway 和结构化输出验证；
- Tool Gateway、最小权限凭据、审批、动作账本与 Reconciler；
- tenant_id 强制传播、T1/T2 隔离、AuditEvent；
- transactional outbox、至少一次消费、CAS、fencing、Checkpoint；
- LangGraph Adapter 和一个第二框架的只读 Adapter；
- 离线评测、质量阈值、安全评审、运行就绪检查、签名 ReleaseManifest；
- 单区域多可用区生产部署、灰度、停止和回滚；
- V1 五个 Evolution Canonical Object 的最小实现：`EvolutionTrigger`、`EvolutionRun`、`GenomeManifest`、`MutationProposal`、`EvolutionAuthorityPolicy`；
- 一个版本化 Subject Profile，能够机器校验 mutable fields / frozen fields / value constraints；
- 一个版本化 Evolution Objective Profile，能够基于既有 EvalResult、业务 KPI、成本、延迟和硬约束比较 candidate vs baseline；
- 一种 `llm_guided_sparse_mutation` Strategy，首期只要求 Single-Candidate、R1/R2、小范围 Mutation；
- L0 最小 Evidence、Run Summary/Fingerprint/rolling aggregate 与 Trigger Gate 的正常路径目标为 0 LLM Token。

### 2.2 选定试点的硬条件

试点业务必须有明确 System of Record、可测试完成条件、可查询写入结果、回滚/补偿负责人和数据 Owner。优先选择“读取多个知识源 → 生成建议 → 人工审批 → 创建工单/草稿”类流程，避免首期直接自动付款、修改核心账务或无人审批的大规模客户触达。

Evolution Vertical Slice SHOULD 选择可安全制造 baseline degradation、结果可测、修复面明确且能回滚的场景。首选：

```text
RAG retrieval_empty / recall / context token
Model schema_invalid / token / route
Tool timeout / rate-limit / provider route
```

首期不要求 R3 大范围 Workflow topology repair 或 R4 自动代码修复。

## 3. 团队与职责

建议核心团队 10–14 人：

| 角色 | 人数 | 90 天主要责任 |
|---|---:|---|
| 产品负责人 / 业务 Owner | 1–2 | 试点范围、完成条件、业务 KPI、Evolution Objective、业务验收、例外裁决 |
| 架构负责人 | 1 | 契约、边界、ADR、Evolution Profile/Strategy 边界、跨流一致性 |
| Runtime/平台工程 | 3–4 | Gateway、State、Coordinator、Adapter、SDK |
| Data/RAG 工程 | 1–2 | Context Builder、检索、来源与删除；RAG Evolution Slice |
| Security/IAM 工程 | 1–2 | PrincipalContext、PDP、凭据、审计、Evolution threat model |
| SRE/平台运维 | 1–2 | CI/CD、部署、可观测、Evidence pipeline、Evolution meta-metrics、容量、恢复 |
| Eval/QA 工程 | 1–2 | 案例集、评分器、baseline/candidate paired eval、回归、故障注入 |

每条工作流必须有单一 DRI。架构负责人维护规范对象和事件目录；任何新增跨模块对象、状态或决定类型必须经过 ADR。Evolution Vertical Slice 复用现有模块，不成立新的独立团队或服务边界。

## 4. 0–30 天：契约闭合与纵向骨架

### 4.1 目标

建立可运行但尚不承载生产写流量的纵向切片，证明请求、状态、框架适配、模型调用和证据链可以闭合；同时提前建立 Evolution 所需 baseline、最小 Evidence 和机器可验证 Mutation Surface，避免第 60 天后才开始设计“怎么进化”。

### 4.2 工作项

| 工作流 | 第 0–10 天 | 第 11–20 天 | 第 21–30 天 |
|---|---|---|---|
| 产品/场景 | 选定一个试点、完成条件、风险与 KPI | 固化输入输出 Schema、人工边界 | 业务样例和失败样例签字 |
| 核心契约 | 发布 v0.1 Schema、状态机、端口、事件目录 | 契约测试与代码生成 | 冻结 MVP 兼容范围 |
| 接入/身份 | HTTP 接入、IdP 验证、tenant_id、幂等 | 边缘 accepted/rejected 事件 | 恶意载荷与重放测试 |
| 状态/运行 | PostgreSQL 表、outbox、queued/admitting 状态 | Run Coordinator、租约、CAS | 崩溃恢复和终态测试 |
| Runtime Adapter | RuntimeAdapter SPI | LangGraph Adapter 最小 start/stream/cancel | 工具意图拦截与事件规范化 |
| 模型/Prompt | PromptContract、ModelRoute | 单模型 Gateway、token/费用计量 | 结构化输出重试与失败语义 |
| 数据/上下文 | 接入一个只读知识源 | ContextManifest、引用和 ACL | 检索质量 baseline |
| Evidence | 定义 L0 事件骨架与 Run Summary | non-blocking TelemetryPort + 聚合 | Fingerprint / rolling window / evidence-gap 可见 |
| Evolution | 定义 GenomeManifest + AuthorityPolicy + Subject Profile | 固化 mutable/frozen field contract | 选定退化场景、baseline Genome 与 Objective Profile |
| 平台/SRE | 开发/集成环境、CI、工件摘要 | OTel 基础、秘密管理 | 首次恢复演练 |

### 4.3 里程碑 M1：可审计只读纵向切片 + Evolution Baseline

第 30 天必须演示：

1. 边缘预校验失败不创建 RunRecord；
2. 预校验成功创建 TaskState 与 RunRecord(queued)；
3. Admission Coordinator 针对 run_id 生成 RunAdmissionResult，状态从 admitting 进入 running；
4. LangGraph Adapter 通过 Model Gateway 完成只读任务；
5. ContextManifest 能列出知识来源、版本、ACL 与 token 分配；
6. RunRecord 提交 phase=terminal、completion_disposition=completed，或提交其他明确 CompletionDisposition；
7. task_id/run_id 可关联到主体、租户、release_id、模型用量、Trace 和 AuditEvent；
8. 每个 Run 可形成最小 Run Summary，稳定路径不调用 Evolution LLM；
9. baseline `GenomeManifest` 可通过 `profile_ref` 解析出 mutable/frozen fields；
10. 一个非法 Mutation 示例（越界数值或 frozen field）能被机器拒绝。

### 4.4 M1 验收门槛

- 核心契约测试 100% 通过，所有线级对象均使用规范名，未出现旧任务、准入或动作别名；
- 相同幂等键并发 100 次只创建一个 Run；
- queued 不可直接进入 running；
- 两租户隔离自动测试通过；
- Coordinator 强制退出后可恢复；
- 敏感输入不出现在普通日志；
- 只读黄金案例成功率达到 90%，且每个答案保留来源引用；
- L0 Collection / Run Summary / Fingerprint 路径目标为 0 LLM Token；
- Mutation Surface Contract 可阻止未授权路径、越界取值和 Governance field 修改。

## 5. 31–60 天：企业副作用、治理与首次离线进化闭环

### 5.1 目标

加入受控写动作、审批、对账、评测和发布证据，使试点具备预生产候选资格；同时完成第一次 **Trigger → Diagnosis → R1/R2 Mutation → Candidate → Offline Eval**，证明 Evolution Kernel 不只是文档对象。

### 5.2 工作项

| 工作流 | 第 31–45 天 | 第 46–60 天 |
|---|---|---|
| Tool Gateway | Tool Catalog、参数 Schema、风险分类、PolicyDecision | 连接一个业务写 API、最小权限凭据、MCP 协议适配 |
| 动作可靠性 | action_key、ActionRecord、ExecutionAttempt | ActionReceipt、unknown/reconciling、Reconciler、补偿入口 |
| 人工流程 | ApprovalRequest、等待/恢复信号 | 过期、撤销、输入变化后重新授权 |
| Runtime | Checkpoint、waiting/paused/retrying | 崩溃、超时、重复、乱序故障注入 |
| Eval | 100–300 个版本化 EvalCase | baseline/candidate paired eval、质量切片、回归基线、评分器校准 |
| Security | 威胁模型、权限矩阵、数据流 | Prompt injection、Evidence poisoning、工具越权、租户泄漏、安全证据 |
| Developer Plane | SDK/CLI、候选构建、SBOM | Adapter Conformance Suite、Mutation constraint validation、内容签名 |
| Evolution | Trigger Candidate + deterministic Gate | EvolutionTrigger + EvolutionRun + Diagnosis/Repair Router + 1 个 R1/R2 MutationProposal |
| Strategy | 固化 `llm_guided_sparse_mutation` I/O 与预算 | Single-Candidate 生成；最多修改 1–2 个字段 |
| SRE | 仪表盘、告警、积压和成本 | Evolution meta-metrics、容量测试、Runbook、备份恢复 |

### 5.3 里程碑 M2：预生产受控写闭环 + 首次离线 Evolution

第 60 天必须演示：

1. 模型或框架产生的 tool/function call 只形成 ToolIntent；
2. Tool Gateway 完成 Schema、PolicyDecision、必要审批、短时凭据和 ActionRecord 预占；
3. 写 API 返回丢失但业务已成功时，ActionRecord 保持 unknown/reconciling，并通过查询收敛，不重复写；
4. Run 在 waiting/approval 后由合法主体恢复，仍绑定原 release_id；
5. QualityGateDecision 与 SecurityGateDecision 各自引用独立证据；
6. ReleaseCandidate 只包含精确版本、内容摘要、SBOM、迁移和回退信息；
7. LangGraph Adapter 通过工具拦截、暂停恢复、事件和租户隔离一致性测试；
8. 人工或故障注入制造的稳定退化形成 Trigger Candidate，并通过 Trigger Gate 形成 `EvolutionTrigger`；
9. `EvolutionRun` 基于有界 A/B/C Evidence 完成 Diagnosis，并选择 R1 或 R2；
10. Strategy 只在 Subject Profile 允许字段内产生一个 `MutationProposal`；
11. Mutation 形成新的 `GenomeManifest` candidate 和既有 `ReleaseCandidate`；
12. Candidate 在同一 baseline / EvalConfig 下得到 Accept 或 Reject 结论，允许以 `no_evolution_needed` / `no_valid_candidate` 正常结束。

### 5.4 M2 验收门槛

- 所有企业写动作 100% 可追溯到 PolicyDecision、ActionRecord 和 ActionReceipt/对账证据；
- 重复副作用率为 0；模拟 1,000 次超时/重复/崩溃无盲目写重试；
- 过期 fencing_token 写入拒绝率 100%；
- 高风险动作在审批或审计不可用时 100% fail closed；
- Eval 关键业务切片达到业务 Owner 设定阈值，且回归差异可解释；
- 恢复演练满足 MVP RPO≤5 分钟、RTO≤30 分钟；
- P95 平台开销、模型延迟和成本分别可见，不混为一个 SLI；
- 普通单次失败不能直接生成 MutationProposal；
- Candidate 每个 change path 都通过 Profile + Authority + constraint 机器校验；
- Candidate 选择可还原到现有 EvalResult + Objective Profile，而不是未解释的单一 Fitness Score。

## 6. 61–90 天：生产化、双框架证明、灰度与 Evolution Canary

### 6.1 目标

完成生产拓扑、第二 Adapter、运行就绪证据和受控灰度，在第 90 天形成可继续扩展的企业平台基线；若 M2 Candidate 被接受，则把它作为低风险 Evolution Candidate 进入 Canary，并验证生产反馈能重新回流 Evidence，而不是用离线分数直接宣布“进化成功”。

### 6.2 工作项

| 工作流 | 第 61–75 天 | 第 76–90 天 |
|---|---|---|
| 部署 | 单区域三可用区、T1/T2 隔离、网络出口 | 灰度路由、排空、回滚、灾备演练 |
| 第二 Adapter | 选择 OpenAI Agents SDK、MAF、Google ADK 或 CrewAI 的只读最小适配 | 同一 AgentDefinition 的等价案例和已知缺口 |
| 发布治理 | OperationalReadinessDecision、ReleaseDecision 聚合 | 签名 ReleaseManifest、撤销和停止 |
| 安全 | 渗透测试、供应链签名、密钥轮换 | SecurityGateDecision 签发和例外到期 |
| Eval | 影子流量、真实分布切片、人工复核 | QualityGateDecision、漂移监控、Objective 对比 |
| Evolution | Candidate human-readable review projection、Canary 前置 | 低风险 accepted Candidate Canary + production feedback；失败则保持 baseline |
| 运营 | 值班、Runbook、SLO、成本预算 | 小流量真实用户、每日 Go/No-Go、Evolution health metrics |
| 文档/交接 | API/Schema/ADR、故障手册 | 服务目录、Owner、下一阶段 Backlog |

### 6.3 里程碑 M3：生产灰度 + 受控 Evolution 反馈

第 75 天进入影子或内部用户流量；第 83 天满足全部决定与运维前置后进入 1%–5% 灰度；第 90 天根据证据扩大到 10%–20%，或保持小流量修复。时间节点不覆盖安全和质量门槛。

如果 Evolution Candidate 通过 M2 离线评测且其 `Promote` 权限允许 Canary，则 M3 至少执行一次受控 Canary。若 Candidate 被拒绝，**拒绝本身仍视为有效 Evolution 闭环证明**，不得为了展示“自动改进”而降低门禁。

### 6.4 M3 验收门槛

- QualityGateDecision、SecurityGateDecision、OperationalReadinessDecision 均为 active，ReleaseDecision 明确目标环境、租户切片、流量上限和回滚版本；
- ReleaseManifest 签名、摘要和工件来源验证通过；
- LangGraph 与第二 Adapter 的只读案例在 TaskState、RunRecord、ContextManifest、审计和终态语义上等价；
- 生产 Adapter 无法直连企业写 API或获取长期凭据；
- 1%–5% 灰度期无 P0/P1 安全事件、无重复副作用、无跨租户泄漏；
- SLO、错误预算、熔断、停止新准入和回滚均实测有效；
- 业务 KPI 相对人工/旧流程达到预先签署的改善阈值，不能只报告模型评分；
- Evolution Candidate 如进入 Canary，线上事实只作为新 Evidence，不覆盖离线 Eval 历史；
- 至少能从 Candidate/Release 追溯到 Trigger、Diagnosis、Mutation、Genome、Eval 与 baseline；
- `trigger_candidate_to_trigger_rate`、`no_evolution_needed_rate`、candidate rejection/regression/safety-block、Evolution cost/time 可观测。

## 7. 发布 Go/No-Go 清单

| 类别 | Go 条件 | No-Go 示例 |
|---|---|---|
| 质量 | 关键切片通过、评分器校准、人工复核一致 | 平均分通过但高风险切片退化 |
| 安全 | 威胁模型闭合、越权/注入/Evidence poisoning 测试通过、例外未过期 | Tool Gateway 存在旁路或 Mutation 触及 frozen field |
| 运行 | 容量、告警、备份恢复、值班和回滚演练通过 | unknown 动作无人对账 |
| 数据 | 驻留、ACL、删除、审计和租户隔离通过 | Vector/缓存跨租户查询 |
| 发布 | 精确版本、签名、回滚版本、灰度上限完整 | 使用 latest 或未签名 Adapter |
| 业务 | Owner、完成条件、人工升级、补偿与 Evolution Objective 明确 | 无人承担错误动作处置或“更好”无法量化 |
| Evolution | Mutation path 可校验、Objective 有 baseline、Budget/stop condition 完整 | 自由 JSON 任意修改、无 baseline 就宣布 improved |

Release Governance 只在所需证据闭合时签发 ReleaseDecision；conditional 必须有条件、期限、负责人和流量上限。任一决定撤销后停止新准入或按清单回滚。

## 8. 明确延期到 90 天之后

以下事项不属于 MVP，不应挤占状态、动作、安全、发布和 Single-Candidate Evolution 闭环：

| 延期项 | 延期原因 | 何时启动 |
|---|---|---|
| 同时完整支持五个 Runtime Adapter | 维护与一致性测试成本高 | M3 稳定后按真实业务需求逐个增加 |
| 通用多 Agent 市场和自由发现 | 容易绕过身份、预算与工具治理 | Capability/Policy 契约稳定后 |
| 自研全套图编排 DSL | 可复用现有框架，非企业差异化核心 | 发现至少三个无法适配的共性缺口后 |
| 跨区域主动-主动运行 | 数据驻留和动作一致性复杂 | 单区域 SLO 与恢复演练稳定两季度后 |
| T3/T4 全物理隔离自动化 | 成本和运维复杂度高 | 有受监管租户和明确商业需求时 |
| 自动长期记忆和组织知识写回 | 删除、来源和错误记忆风险高 | Memory 治理、TTL、人工复核成熟后 |
| 自主高风险交易与无人审批执行 | 责任与补偿风险不可接受 | 法务/风控批准并有可逆业务协议后 |
| 动态跨框架运行中迁移 | Checkpoint 语义不可直接等价 | Adapter 状态映射和迁移证据成熟后 |
| 完整低代码 Studio | 不影响运行闭环 | SDK/CLI 使用数据证明重复需求后 |
| 复杂计费和内部市场结算 | 首期用用量账本即可 | 多部门规模化使用后 |
| R3 大范围 Workflow topology 自动修复 | Eval/Canary 面更大 | R1/R2 Evolution 闭环稳定后 |
| R4 自动代码生成与修复 | 供应链、Sandbox、安全成本高 | R1/R2 稳定且 R4 安全门禁成熟后 |
| Gene Pool / Species / Population / 自动跨 Agent 传播 | 属于 V2 | V2 通过 ADR 进入 Current 后 |

延期不等于忽略：MVP Schema 和端口应保留可演进空间，但不实现未经验证的抽象。

## 9. 关键风险与缓解

| 风险 | 领先指标 | 缓解 |
|---|---|---|
| 范围膨胀 | 同时接入多个业务域/模型/写系统 | 单试点、单模型、最多两个写动作、Single-Candidate Evolution |
| 框架侵入 UEAF 语义 | 使用框架 Session/Task 作为权威 | Adapter Conformance + 存储所有权测试 |
| 只做 Happy Path | 无 unknown、重复、暂停场景 | 第 31 天起持续故障注入 |
| 评测代表性不足 | 线上失败集中在未覆盖切片 | 从真实分布构建版本化 EvalCase |
| 安全在末期介入 | 第 60 天后才发现数据流问题 | 第 0 天 Security DRI 与威胁模型 |
| 业务系统不可对账 | 超时后无法确认是否成功 | 试点硬条件要求查询/幂等/补偿 |
| 运维被模型噪声淹没 | 单一全局成功率 | 按阶段、租户、风险和依赖拆 SLI |
| Evolution 只存在于文档 | 第 60 天仍无 Trigger/Mutation/Eval demo | M1 建 baseline，M2 必须完成离线 Single-Candidate 闭环 |
| Evolution 被污染 Evidence 驱动 | Trigger 激增、单一来源主导、重复 Proposal | provenance + A/B/C 对照 + injection detection + novelty/cooldown |
| 以大改代替诊断 | candidate scope 持续扩大 | Smallest Effective Repair + Profile mutation limits |

## 10. 每周治理节奏

- 每日：工程阻塞、风险、生产/预生产异常和动作对账积压；
- 每周：契约变更评审、Eval 回归、安全缺口、SLO/成本、试点 KPI、Evolution Trigger/Cost/Reject 指标；
- 每两周：里程碑演示、业务 Owner 验收、Backlog 减法；
- 第 30/60/75/83/90 天：正式证据评审和继续/停止决定；
- P0 安全、跨租户泄漏或重复高风险副作用：立即停止新准入，不等待例会。

## 11. 90 天完成定义

只有同时满足以下条件，MVP 才算完成：

1. 一个真实试点在生产灰度运行，并有业务 Owner 签字；
2. 两级接入/准入、状态机、Context/Model/Tool Gateway、ActionRecord 和审计链完整；
3. LangGraph 加第二个只读 Adapter 证明企业契约可移植；
4. 四类发布相关决定边界清晰，ReleaseManifest 可签名、撤销、灰度和回滚；
5. 重复、超时、崩溃、等待、恢复、取消、对账和租户隔离均有自动化验收；
6. SLO、Runbook、值班、备份恢复、成本和安全响应已移交运营；
7. V1 五个 Evolution Canonical Object 已最小落地，未新增第二套 Candidate/Eval/Budget/Lineage/Fitness 真相源；
8. 至少一次完整 `Trigger -> EvolutionRun -> Diagnosis -> MutationProposal -> GenomeManifest candidate -> ReleaseCandidate -> Eval -> Accept/Reject` 可重复演示；
9. Mutation Surface 可以机器校验，Objective Profile 可以解释 candidate 相对 baseline 的业务/质量/成本/延迟 trade-off；
10. 正常 Evidence Collection/Aggregation/Trigger Candidate 路径目标为 0 LLM Token，Evidence Expansion 有界；
11. Evolution Human Review Projection 和 Evolution-specific threat model 至少覆盖当前试点；
12. 延期项有明确触发条件，没有以半成品方式混入生产路径。
