# ADR-015：采用分层诊断与最小有效修复路由

- 状态：Accepted
- 决策日期：2026-08-14
- Architecture Generation：V1
- Implementation：Current

## 背景

UEAF V1 已经能够从 Runtime、Model、RAG、Tool、Workflow、Security、Eval 等模块自动采集 Evidence，并通过 Trigger Gate 形成 `EvolutionTrigger`。

下一步风险是：如果每个基层模块在发现问题后直接修改自己，会形成多个局部自修系统。例如 RAG 自动改 top_k、Tool 自动增加 retry、Workflow 自动换 Tool，而 Evolution Kernel 又同时改变 Workflow 或 Prompt，最终出现局部优化冲突、版本漂移和不可追溯修改。

同时，问题出现的层级并不一定等于真正的根因或修复目标：Tool schema failure 可能来自 Model 参数生成错误，RAG empty 可能来自 ACL、source freshness 或 Provider 故障。

## 决策

### 1. 基层只检测与止血，长期修复统一进入 Evolution

模块 02–09 可以检测问题并执行当前 Release 已授权的 Operational Mitigation，但不得因检测到问题而原地改写长期 Prompt、Policy、Workflow、Tool Code、Model Route 或 Genome。

长期修复统一由模块 11 完成 Diagnosis 与 Repair Routing，并通过现有 `MutationProposal -> GenomeManifest -> ReleaseCandidate -> Eval -> Release` 链执行。

### 2. 采用 Repair Ladder

V1 使用：

```text
R0 Operational Mitigation
R1 Parameter / Config Repair
R2 Component / Routing Repair
R3 Workflow / Composition Repair
R4 Artifact / Code Repair
R5 Governance Boundary
```

R0 不改变长期 Genome；R1–R4 必须产生 Candidate；R5 不允许同一递归链自动修复。

### 3. Smallest Effective Repair

默认选择能够合理解决问题的最小修复范围。能用 R1 解决时不得无证据扩大到 R2/R3/R4。

修复层级升级必须有新的诊断证据或失败证据支持，而不是“上一 Candidate 失败，所以扩大修改范围”。

### 4. 问题发生层与 Repair Target 分离

Repair Router 必须允许：

```text
observed_problem_scope != likely_root_cause_scope != repair_target_scope
```

例如：

- Tool invalid args -> 可能修 Prompt/Model schema；
- RAG empty -> 可能修 query/retrieval route，也可能只路由到 source/security owner；
- Workflow latency -> 可能修 Tool/Model component，而非 Workflow topology。

### 5. Repair Router 不成为新 Domain

`Repair Router`、Diagnosis、RepairLevel、RepairHistory 都是模块 11 内部策略、Projection 或 metadata，不新增新的 Canonical Object 或独立服务。

V1 仍只保留既有五个 Evolution Canonical Object。

### 6. 扩展 `MutationProposal`

`MutationProposal` SHOULD 记录：

```yaml
diagnosis_refs: [string]
repair_level: r1 | r2 | r3 | r4
repair_target_scope: [string]
repair_reason_codes: [string]
```

R0/R5 不生成自动 MutationProposal。

### 7. Governance 不可通过“修复”绕过

ACL、Identity、Permission、PDP/PEP、Secrets、Tool Gateway enforcement、Audit root、Eval root、Release Authority、Budget Enforcement、kill switch、legal hold、deletion policy 等属于 R5。

如果问题表现为“权限不足导致任务失败”，Evolution 可以修错误 Tool/Router/Prompt，但不能自动给自己更多权限。

### 8. Tool unknown 先对账

Tool timeout/unknown 不能直接作为“增加 retry”证据。必须先遵守 ActionRecord/ActionReceipt 的 outcome certainty 与 reconciliation 语义，再决定长期 timeout、provider、polling 或 workflow 修复。

## 后果

- RAG/Tool/Workflow 等基层模块不会形成互相冲突的自治自修系统；
- 修复范围更小，Candidate、Eval、Token 和回归成本降低；
- 可以跨层定位 root cause，不把症状误当修复目标；
- Governance 权限不能借“修复失败”被自动放宽；
- 模块 11 需要维护可解释的诊断与修复路由逻辑；
- 高层 R3/R4 修复速度可能比直接大改更慢，但可显著降低系统性回归风险。

## 重审条件

- 实际运行证明逐级修复导致关键问题长期无法解决；
- 某业务域具备可靠的形式化根因定位，可安全直接选择较高 Repair Level；
- V2 生态共同进化需要跨 Species 的 Repair Routing；
- 现有 `MutationProposal` 无法容纳必要诊断/修复证据，需要重新评估 Canonical Object 边界。
