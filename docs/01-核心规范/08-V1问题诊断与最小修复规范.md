# UEAF V1 问题诊断与最小修复规范

版本：`0.1.0-draft`  
规范状态：Draft  
Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 范围

本文定义 UEAF V1 在 `EvolutionTrigger` 已成立之后，如何完成问题诊断、根因定位、修复目标选择、修复层级选择和 `MutationProposal` 生成。

目标不是让 RAG、Tool、Workflow、Model 等基层模块各自形成独立“自修复 Agent”，而是保持统一职责：

```text
基层模块
  -> 发现事实
  -> 必要时即时止血
  -> 输出 Evidence

Evolution Kernel
  -> 诊断根因
  -> 选择最小长期修复
  -> 产生 MutationProposal

Existing Build / Eval / Release
  -> 构建候选
  -> 证明修复有效
  -> 决定是否发布
```

核心原则：

> **问题发生在哪一层，不代表修复就一定发生在哪一层。**

## 2. 修复职责边界

### 2.1 基层模块拥有

模块 02–09 MAY：

- 检测异常、失败、漂移和容量问题；
- 执行其既有职责内的即时 Operational Mitigation；
- 输出结构化 Evidence、状态和 mitigation refs；
- 执行当前 `ReleaseManifest` 已授权的 fallback、retry、reconciliation、rollback、degrade、rate-limit 等机制。

基层模块 MUST NOT 因检测到问题而原地修改其长期 Prompt、Policy、Tool Code、Workflow、Model Route、Memory Policy 或当前 `ReleaseManifest`。

### 2.2 Evolution Kernel 拥有

模块 11 负责：

- 基于 Trigger + Evidence Expansion 形成诊断；
- 判断真正 root cause scope；
- 选择最小有效修复层级；
- 检查 `EvolutionAuthorityPolicy`；
- 创建有限 `MutationProposal`；
- 将候选送入既有 Build/Eval/Release 流程。

模块 11 不执行生产事故止血，也不直接写生产配置。

## 3. Repair Ladder

V1 使用 Repair Ladder 约束修复升级顺序。`RepairLevel` 是版本化 Policy/Config/Proposal metadata，不新增 Canonical Object。

| Level | 名称 | 作用 | 是否产生 Mutation |
|---|---|---|---|
| `R0` | Operational Mitigation | 解决当前运行风险：fallback、rollback、reconcile、degrade、rate-limit、isolate | 否 |
| `R1` | Parameter / Config Repair | 调整参数、阈值、路由权重、timeout、top_k 等局部配置 | 是 |
| `R2` | Component / Routing Repair | 替换/切换模型、Retriever、Tool、Provider、Router、版本化组件 | 是 |
| `R3` | Workflow / Composition Repair | 修改节点顺序、验证环节、Agent/Tool 组合、拓扑和流程策略 | 是 |
| `R4` | Artifact / Code Repair | 修改 Tool/Adapter/Skill/代码工件，生成新版本候选 | 是 |
| `R5` | Governance Boundary | Identity、Permission、PDP/PEP、Audit、Eval Root、Release Authority、Secrets 等 | 禁止自动修复 |

规则：

1. R0 不属于长期演化；
2. R1–R4 必须形成 Candidate，不原地修改生产；
3. R5 只能路由到独立治理/人工变更，不得由同一递归链自主修改；
4. 默认从最低可行层开始，不得无证据跳到更大范围修改。

## 4. Smallest Effective Repair

UEAF V1 采用 **Smallest Effective Repair（最小有效修复）** 原则：

```text
能用 R1 解决
  -> 不进入 R2

R1 无法解决或证据明确指向组件
  -> R2

R2 无法解决或根因属于组合/流程
  -> R3

R3 无法解决且证据明确指向实现缺陷
  -> R4

涉及 Governance Kernel
  -> R5 / route to owner
```

修复层级 MUST 由证据支持，不得仅因为强模型认为“大改可能更好”就扩大 mutable scope。

## 5. Diagnosis 与 Repair Router

V1 MAY 在模块 11 内实现 `Repair Router`，但它是内部逻辑组件，不是新的服务或 Canonical Object。

推荐输入：

```text
EvolutionTrigger
Evidence Expansion result
baseline GenomeManifest
EvolutionAuthorityPolicy
operational mitigation refs
previous mutation / eval refs
```

Repair Router 输出只允许三类语义：

```text
NO_EVOLUTION
  当前无需长期修改

OPERATIONAL_ONLY
  继续使用/调整既有运行处置，但不修改 Genome

MUTATION
  生成 R1 / R2 / R3 / R4 MutationProposal
```

内部 Diagnosis MAY 保存为 Projection/attempt metadata，例如：

```yaml
observed_problem_scope: rag | model | tool | workflow | memory | runtime | security | mixed
likely_root_cause_scope: string
confidence: number
supporting_refs: [string]
contradicting_refs: [string]
recommended_repair_level: r1 | r2 | r3 | r4 | r5 | none
recommended_target_scope: [string]
```

它不得成为第二套权威状态。

## 6. 问题发生层与修复层分离

### 6.1 Tool 失败不一定修 Tool

例如：

```text
Tool schema invalid ↑
  -> 可能是 Model 持续生成错误参数
  -> Repair Target = Prompt / Tool selection / structured output
```

而不是自动修改 Tool。

### 6.2 RAG 失败不一定修 Retriever

例如：

```text
retrieval_empty ↑
  -> 可能是 source sync / ACL / query rewrite / index / provider outage
```

必须先诊断再确定修复目标。

### 6.3 Workflow 失败可能来自下游组件

高 fan-out、高 retry 或长延迟可能来自 Tool/Model 退化；不得因为 Workflow 指标恶化就默认重写拓扑。

## 7. RAG 修复矩阵

| Observed Problem | 首要诊断 | 常见 Repair Target | 推荐 Level | 禁止行为 |
|---|---|---|---|---|
| `retrieval_empty` | source freshness、ACL、query、index、provider health | query policy / retrieval policy / source route | R1/R2 | 自动放宽 ACL |
| Recall 低 | embedding、chunking、top_k、query formulation | top_k / query rewrite / embedding / hybrid retrieval | R1/R2/R3 | 直接全量扩大 Context |
| Precision 低 | rerank、filter、query ambiguity | rerank threshold / metadata filter / retriever | R1/R2 | 通过删除安全过滤提高命中 |
| Context 过大 | selected chunks、token budget、duplicate evidence | selection / compression / top_k | R1/R3 | 无限增加 Context budget |
| Citation 错误 | evidence mapping、generation/verification | citation policy / verification workflow | R1/R3 | 无 Evidence 仍伪造引用 |
| 数据过期 | sync/index freshness | refresh route / indexing config / upstream owner | R1/R2/Operational | 直接覆盖业务事实 |
| 延迟高 | retriever/reranker/provider | cache / top_k / routing / provider | R1/R2 | 牺牲权限过滤换速度 |
| ACL 导致不可见 | 授权是否正确 | Governance owner / task design | R5/none | AI 自行增加权限 |

## 8. Model / Prompt 修复矩阵

| Observed Problem | 首要诊断 | 常见 Repair Target | Level |
|---|---|---|---|
| Schema invalid | Prompt contract、model capability、temperature | Prompt / schema strategy / model route | R1/R2 |
| Hallucination/事实错误 | Evidence quality、Prompt、model、verification | Prompt / Context / verifier workflow / model route | R1/R2/R3 |
| Token 过高 | Prompt、Context、retry、planning loops | prompt/context budget / route / workflow | R1/R2/R3 |
| Provider error/限流 | provider health、route、quota | fallback route / provider / backoff config | R0/R1/R2 |
| 某 task slice 能力不足 | task routing、model specialization | model route / specialist workflow | R2/R3 |

## 9. Tool 修复矩阵

| Observed Problem | 首要诊断 | 即时处理 | 长期 Repair | Level |
|---|---|---|---|---|
| Timeout | `outcome_certainty`、provider health | unknown -> reconciliation；禁止盲目 retry | timeout/polling/async route/provider | R0/R1/R2/R3 |
| Rate limit | quota、fan-out、batchability | backoff / throttle | batch/cache/provider/routing | R0/R1/R2 |
| Schema mismatch | API/Adapter version | fail closed / fallback if valid | Adapter/Tool version | R2/R4 |
| Tool 参数错误 | Model/Prompt 是否构造错误 | reject invalid intent | Prompt/schema/tool-selection | R1/R2 |
| Permission denied | 调用是否错误、权限是否真的缺失 | deny | Router/Prompt；若确需权限则 route governance | R1/R2/R5 |
| 结果质量下降 | upstream data、Tool implementation、provider | fallback if available | component/provider/code | R2/R4 |

### 9.1 Tool timeout 特殊规则

`timeout` MUST NOT 被等价为 `certain_failure`。

```text
Tool timeout
  -> outcome certainty unknown?
  -> reconcile first
  -> only after authoritative outcome may diagnose long-term retry/timeout policy
```

Evolution MUST NOT 仅因 timeout 计数增加就提出无条件增加 retry_count。

## 10. Workflow / Multi-Agent 修复矩阵

| Observed Problem | 首要诊断 | Repair Target | Level |
|---|---|---|---|
| fan-out 过高 | 路由、重复 handoff、下游失败 | routing / branch policy / topology | R1/R3 |
| retry loop | root dependency、stop policy | retry/stop policy / component | R1/R2/R3 |
| 节点长期失败 | node implementation 或输入质量 | upstream prompt/context/tool/skill | R1/R2/R4 |
| 延迟过高 | critical path、串并行、Tool/Model latency | topology / route / component | R2/R3 |
| 多 Agent 结果冲突 | role overlap、judge/merge policy | composition / verifier / merge policy | R1/R3 |

## 11. Memory 修复矩阵

| Observed Problem | 首要诊断 | Repair Target | Level |
|---|---|---|---|
| 错误记忆被召回 | write quality、confidence、scope | retrieval/write policy、invalidations | R1/R2 |
| Memory Context 膨胀 | active set、duplicate、retention | retrieval cap / consolidation / eviction | R1/R3 |
| 新旧记忆冲突 | provenance、freshness、supersession | ranking / supersession policy | R1/R2 |
| 跨租户/越权记忆 | security boundary | Security/Governance | R5；立即 containment |

## 12. Runtime / Adapter 修复矩阵

| Observed Problem | 首要诊断 | Repair Target | Level |
|---|---|---|---|
| Provider/Adapter crash | runtime compatibility、provider state | restart/fallback；Adapter candidate if recurrent | R0/R2/R4 |
| 状态恢复失败 | checkpoint/schema/version | compatibility / migration / Adapter | R2/R3/R4 |
| 事件乱序/缺失 | adapter semantics、queue | ordering/dedup config / Adapter | R1/R4 |
| 成本/延迟漂移 | model/tool/context/workflow attribution | implicated component | R1–R3 |

## 13. Governance Boundary

以下问题即使影响成功率，也不得通过自动演化“修复”为更宽权限：

- ACL / data classification；
- Identity / delegation；
- PDP / PEP；
- Secret / Credential；
- Tool Gateway enforcement；
- Audit root；
- Eval root / holdout / threshold root；
- Release Authority；
- Budget Enforcement；
- kill switch / legal hold / deletion policy。

Repair Router 对这类根因 MUST 返回 `R5 / route_to_governance` 或 `NO_EVOLUTION`，不得产生提升权限的 MutationProposal。

## 14. `MutationProposal` 修复字段

在本规范下，V1 `MutationProposal` SHOULD 增加以下字段；它仍是既有五个 Canonical Object 之一，不新增 Repair 对象：

```yaml
diagnosis_refs: [string]
repair_level: r1 | r2 | r3 | r4
repair_target_scope: [string]
repair_reason_codes: [string]
```

规则：

- `repair_level` 只能为 R1–R4；
- R0 不产生 MutationProposal；
- R5 不产生自动 MutationProposal；
- `repair_target_scope` MUST 是 `EvolutionAuthorityPolicy` 和本轮 `mutable_scope` 的交集；
- Proposal MUST 可追溯到 Trigger、Evidence、Diagnosis 和 baseline Genome。

## 15. Eval 要求随修复层级升级

| Level | 最小 Eval |
|---|---|
| R1 | Targeted deterministic/statistical eval + direct regression |
| R2 | Targeted eval + compatibility + regression + Canary by risk |
| R3 | Workflow/trajectory eval + regression + performance + Canary |
| R4 | Unit/integration/security/compatibility/benchmark + full relevant release gates |

任何安全硬失败均停止后续晋升；高层修复不能用更高“能力收益”抵消安全失败。

## 16. 修复升级与停止

单个 EvolutionRun SHOULD 优先尝试最低合理 Repair Level。

```text
R1 candidate fails
  -> diagnose whether same hypothesis invalid
  -> only with new evidence may escalate R2

R2 fails
  -> only if root cause indicates composition may escalate R3

R3 fails
  -> only if implementation defect is supported may escalate R4
```

不得用“不断扩大修改范围”替代真实诊断。若证据不足、预算不足或没有可信修复方向，应终止为 `no_evolution_needed` / `no_valid_candidate` / `budget_exhausted`。

## 17. 修复经验复用

V1 不新增 RepairHistory 真相源。修复历史由：

```text
EvolutionTrigger
Diagnosis/attempt metadata
MutationProposal
GenomeManifest.parent_refs
EvalResult
ReleaseManifest
Production feedback
```

形成 Projection。

后续相似问题 SHOULD 优先检索已验证成功/失败的修复路径，避免重复模型推理和重复实验。

## 18. V1 验收条件

1. RAG/Tool/Workflow 发生异常时，基层模块不会原地修改长期配置或代码；
2. Tool timeout + unknown 先进入 reconciliation，不会被 Evolution 自动转换为盲目 retry；
3. Repair Router 能区分问题发生层与 root cause/repair target；
4. 默认优先 R1，只有证据支持时才升级 R2/R3/R4；
5. R5 Governance 问题无法生成自动提升权限的 MutationProposal；
6. 每个 MutationProposal 可还原 diagnosis refs、repair level、target scope 和 Trigger；
7. R1–R4 Candidate 仍复用模块 10/08/07/09 的 Build/Eval/Release；
8. 未新增 RepairPlan、DiagnosisResult、RepairHistory 等跨模块 Canonical Object。
