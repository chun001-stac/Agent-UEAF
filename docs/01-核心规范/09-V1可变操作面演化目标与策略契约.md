# UEAF V1 可变操作面、演化目标与策略契约

版本：`0.2.0-draft`  
规范状态：Draft  
Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 范围

本文补齐 UEAF V1 Controlled Evolution Kernel 的三个执行问题：

1. **进化什么**：把 `GenomeManifest.profile_ref` 解析为机器可验证的可变操作面；
2. **怎样算更好**：通过版本化 Evolution Objective / Fitness Profile 解释既有 `EvalResult`，形成候选相对 baseline 的选择规则；
3. **怎样搜索**：定义 `EvolutionStrategy` 的最小输入、输出、预算和候选生成约束。

本文同时明确 V1 五类 `subject_type`：

```text
agent | skill | tool | workflow | strategy
```

的默认 Mutation Surface。本文不新增第六个 Evolution Canonical Object，也不建设独立 GeneSpace、Fitness、Experiment、Strategy、Prompt、ContextPolicy 或 ModelRoute Domain。

所有表达复用：

```text
GenomeManifest.profile_ref
Registry metadata / versioned Profile
EvolutionAuthorityPolicy
MutationProposal
EvalConfig / EvalResult / Gate
BudgetEnvelope / Budget Ledger
ReleaseCandidate / ReleaseManifest
Artifact / Registry
```

## 2. 核心原则

1. **Agent 负责组合，组件负责自身细节。** 能修改版本化 component/profile ref 时，不把组件内部参数重复塞进 Agent Genome。
2. **Mutable Scope 必须继续下钻到 Mutable Field。** `mutable_scope=[context_policy]` 不能直接授权任意 JSON 修改。
3. **每个 Mutation 必须先通过机器校验，再进入 Candidate Build。** LLM 不能通过自由 `change_summary` 绕过字段、范围、类型或跨字段约束。
4. **Replace-by-reference 优先于原地改内容。** Prompt、Model Route、Context Policy、Memory Policy、Schema、Workflow、Skill、Tool 等版本化资产优先产生新版本 ref。
5. **Fitness 不是新的真相源。** 选择结果必须可还原到现有 `EvalResult`、成本、延迟、安全与业务 KPI 证据。
6. **Gate 与 Optimization Objective 分离。** Gate 回答“能否接受”，Objective 回答“在可接受候选中哪个更值得推进”。
7. **安全与治理硬约束不可被权重抵消。** 安全硬失败、权限越界、治理边界违规不能因业务收益较高而被总分覆盖。
8. **Sparse Mutation 必须可度量。** 单次候选最多修改多少字段、组件和 scope 必须由 Profile/Strategy Policy 明确约束。
9. **搜索预算有界。** Candidate 数、模型调用、Token、金额、wall time、重复尝试和强模型调用受既有 Budget 约束。
10. **V1 不做生态级自动传播。** 成功能力可以沉淀为版本化 Artifact 并由其他 Agent 后续通过普通 Mutation 复用，但自动发现/传播/Gene Pool 属于 V2。

## 3. Mutation Surface Contract

### 3.1 Subject Profile

`GenomeManifest.profile_ref` MUST 指向版本化 Subject Profile。该 Profile 除定义必需组件和兼容规则外，还必须定义 Mutation Surface Contract。

推荐结构：

```yaml
profile_id: agent-standard-v1
subject_type: agent
schema_version: 1

mutable_fields: []
bounded_fields: []
replace_only_fields: []
conditional_fields: []
frozen_fields: []
cross_field_constraints: []
mutation_limits: {}
```

字段类别语义：

```text
mutable
  可直接产生新值，但仍受类型、兼容性和 Authority 约束

bounded
  可修改，但必须满足 min/max/enum/step/schema 等边界

replace_only
  不允许修改被引用内容，只允许切换到 Registry 中有效的新版本 ref

conditional
  只有满足指定 RepairLevel、risk、Eval、Canary 或 Human Review 条件时允许变化

frozen
  当前递归链禁止修改
```

每个可变字段 SHOULD 描述：

```text
path
value type
allowed operations
range / enum / registry constraints
compatibility checks
risk class
minimum repair level when applicable
requires canary / human review when applicable
```

### 3.2 Effective Mutation Surface

真正允许本轮修改的字段不是单一 Profile 决定，而是以下交集：

```text
Subject Profile 可变字段
∩ EvolutionAuthorityPolicy
∩ EvolutionRun.mutable_scope
∩ Repair Router.repair_target_scope
∩ 当前环境/风险 Profile
= Effective Mutation Surface
```

任一层 deny，最终均不得修改。

### 3.3 Governance Frozen Root

无论普通 Profile 如何配置，以下 Governance Kernel 均 MUST frozen：

```text
Identity / Delegation root
Permission / PDP / PEP
Tool Gateway enforcement
Secrets / Credentials
Audit root
Eval root / holdout / threshold root
Release Authority
Budget Enforcement
Kill switch / Legal Hold / Deletion root
```

当前 `ReleaseManifest` 也不得原地修改。

## 4. MutationProposal 机器可验证 Patch

`MutationProposal.change_summary` 继续用于人类摘要，但机器执行 MUST 使用结构化 `changes[]`。

推荐：

```yaml
changes:
  - target_ref: context-policy-12
    path: retrieval_top_k
    operation: replace
    before: 5
    after: 8
    constraint_profile_ref: context-policy-standard-v1
```

每条 change MUST 满足：

```text
path 属于 Effective Mutation Surface
operation 被字段允许
before 与 baseline 一致或可证明 superseded
new value 满足 type/range/enum/ref/schema 约束
目标 ref 属于允许 Registry
跨字段约束仍成立
不触碰 frozen field
不扩大 Authority
```

任一条件失败，Candidate Build MUST 拒绝，不允许由 LLM 解释为“意图正确所以继续”。

V1 SHOULD 支持对 `changes[]` 计算 deterministic diff hash，用于重复 Proposal 检测、审计和 Candidate provenance。

## 5. `subject_type=agent`

### 5.1 定位

Agent 是组合与运行身份层，不应成为 Prompt、Model、RAG、Tool、Workflow 参数的大杂烩。

推荐 Agent Profile：

```yaml
agent_profile:
  prompt_ref: string
  model_route_ref: string
  context_policy_ref: string
  memory_policy_ref: string | null
  workflow_ref: string | null
  skill_refs: [string]
  tool_policy_ref: string
  capability_refs: [string]
  task_routing_policy_ref: string | null
  behavior:
    reasoning_budget_class: low | medium | high
    fallback_mode: none | conservative | alternate_route
    max_internal_steps: integer
```

### 5.2 Agent Replace-only

以下 SHOULD 以 ref replacement 为主：

```text
prompt_ref
model_route_ref
context_policy_ref
memory_policy_ref
workflow_ref
tool_policy_ref
skill_refs[]
capability_refs[]
task_routing_policy_ref
```

具体 Prompt 文本、temperature、retrieval_top_k、Tool timeout、Workflow topology 不应直接重复成为 Agent-level field；它们属于被引用 Profile/Artifact 的自身操作面。

### 5.3 Agent Bounded

```text
behavior.reasoning_budget_class
behavior.fallback_mode
behavior.max_internal_steps
```

具体枚举和上下限由 Subject Profile 定义，不由框架硬编码。

### 5.4 Agent Conditional

以下变化影响组合结构，SHOULD 根据风险要求 R2/R3、Canary 或 Gated Promote：

```text
workflow_ref
skill_refs[]
capability_refs[]
tool_policy_ref
```

单纯兼容版本替换 MAY 为 R2；真正改变工作流组合或执行拓扑通常属于 R3。

### 5.5 Agent Frozen

除 Governance Kernel 外，Agent MUST NOT 通过 Mutation 改变：

```text
agent identity root
tenant ownership
permission root
secret scope
release authority
evaluator root
budget enforcement
```

## 6. `subject_type=skill`

### 6.1 定位

Skill 是可复用、版本化能力单元，可以由 instruction、schema、依赖和 implementation artifact 组成，但不拥有身份或权限根。

推荐：

```yaml
skill_profile:
  instruction_ref: string
  input_schema_ref: string
  output_schema_ref: string
  model_requirement_ref: string | null
  context_policy_ref: string | null
  allowed_tool_refs: [string]
  dependency_refs: [string]
  implementation_ref: string | null
  behavior:
    max_steps: integer
    confidence_threshold: number
```

### 6.2 Skill R1 / Bounded

典型 R1：

```text
behavior.max_steps
behavior.confidence_threshold
context_policy_ref
model_requirement_ref
```

`instruction_ref` MAY 产生新版本，但 SHOULD 以版本化 ref replacement 进入 Candidate，而非直接改生产正文。

### 6.3 Skill Replace-only / R2

```text
instruction_ref
input_schema_ref
output_schema_ref
model_requirement_ref
context_policy_ref
dependency_refs[]
allowed_tool_refs[]
```

Tool dependency replacement 不等于权限授予。新 Tool ref 只有在当前主体已有对应 Authority/Policy 时才能进入 Effective Mutation Surface。

### 6.4 Skill R4

代码型 Skill 的：

```text
implementation_ref
```

只能通过新 Artifact → sandbox/tests/security/compatibility → ReleaseCandidate 替换。

### 6.5 Skill Frozen

Skill 不能修改 tenant ownership、permission root、credential、Tool Gateway enforcement、Audit root、Release Authority、Eval holdout 或 Budget Enforcement。

如果 Skill 需要当前权限之外的 Tool，Repair Router 必须路由 R5，而不是自动扩大 `allowed_tool_refs` 的授权范围。

## 7. `subject_type=tool`

### 7.1 定位

Tool 可能产生真实副作用，因此默认 Mutation Surface 比其他 Subject 更严格。

推荐：

```yaml
tool_profile:
  interface_schema_ref: string
  adapter_ref: string
  provider_route_ref: string
  operation_class: read | write | destructive
  execution_mode: sync | async
  timeout_policy_ref: string
  retry_policy_ref: string
  reconciliation_policy_ref: string
  result_schema_ref: string
  implementation_ref: string | null
```

### 7.2 Tool R1

可在 Profile 边界内调整：

```text
timeout / polling / backoff
batch size
rate-limit behavior
cache policy
provider routing weights
```

Tool timeout 的任何修复仍必须遵守：

```text
timeout != certain_failure
outcome_certainty=unknown -> reconciliation first
```

因此 timeout 上升不能机械生成 `retry_count ↑` Proposal。

### 7.3 Tool R2

典型 replace-only：

```text
provider_route_ref
adapter_ref
tool/component version ref
interface/result schema ref when compatibility proven
```

### 7.4 Tool R4

```text
implementation_ref
adapter implementation
schema conversion code
```

只能通过新 Artifact 和完整 R4 Build/Eval/Security 流程。

### 7.5 Tool Frozen

以下不得自动修改：

```text
operation risk classification root
permission requirements
credential scope
identity binding
PDP/PEP
Tool Gateway enforcement
approval requirement root
audit requirement
action idempotency / outcome-certainty semantic root
release authority
```

`PermissionDenied` 不能被修复为自动降低权限要求。

### 7.6 Destructive Tool

`operation_class=destructive` 的 Profile SHOULD 默认收紧：

```text
Experiment = isolated/gated
Promote = gated or never
requires human review = true when policy requires
```

普通 Profile 不得通过 Evolution 把 destructive Tool 降级成低风险分类。

## 8. `subject_type=workflow`

### 8.1 定位

Workflow 表示步骤、节点、依赖、分支、合并、验证和 Agent/Skill/Tool composition，是 R3 的主要目标。

推荐：

```yaml
workflow_profile:
  node_refs: [string]
  edge_policy_ref: string
  entry_node: string
  terminal_nodes: [string]
  routing_policy_ref: string
  retry_policy_ref: string
  stop_policy_ref: string
  verification_policy_ref: string | null
  merge_policy_ref: string | null
  max_fanout: integer
  max_depth: integer
```

### 8.2 Workflow R1

```text
routing/branch threshold
max_fanout
max_depth
retry limit
stop threshold
timeout
merge threshold
verification threshold
```

均必须 bounded。

### 8.3 Workflow R2

在拓扑不变时替换节点组件：

```text
model component
skill
tool
sub-agent
provider route
```

可视为 Component / Routing Repair。

### 8.4 Workflow R3

以下属于 Composition/Topology Repair：

```text
add/remove/replace node
change ordering
serial <-> parallel
change branching or merge
change handoff
add verification stage
add/remove specialist
remove redundant agent/tool stage
```

### 8.5 Workflow Frozen Control Nodes

以下如果由安全/业务/监管 Profile 声明 mandatory，则 MUST frozen：

```text
mandatory approval node
security enforcement node
audit boundary
Tool Gateway boundary
tenant boundary
mandatory reconciliation
mandatory release gate
regulatory control node
```

不得因为 latency 或成本上升自动删除强制审批/安全节点。

### 8.6 Workflow Cross-field Constraints

至少支持下列语义约束：

```text
使用 destructive Tool -> 必须存在所需 approval/confirmation path
存在 side effect -> 必须经过 Tool Gateway
max_fanout 增大 -> concurrency/budget 仍满足
retry>0 且 outcome 可 unknown -> reconciliation path 必须存在
跨 Agent handoff -> Principal/Delegation Context 必须传播
```

## 9. `subject_type=strategy`

### 9.1 定位

V1 Strategy 可表示 planning、routing、selection、retrieval、tool-selection 或 candidate-generation 等决策/搜索逻辑。Strategy 本身不是 V3 Meta Evolution。

推荐：

```yaml
strategy_profile:
  strategy_type: string
  implementation_ref: string
  parameter_schema_ref: string
  parameter_values: object
  applicable_scope: [string]
  dependency_refs: [string]
  max_steps: integer
  exploration_budget: integer
```

### 9.2 Strategy R1

可 bounded 调整：

```text
parameter_values
thresholds
weights
exploration budget
max steps
selection cutoff
```

### 9.3 Strategy R2 / R4

已有 Strategy implementation/component replacement 可为 R2；生成新的 executable implementation 必须作为 R4 Artifact。

### 9.4 Strategy Frozen

Strategy 永远不能在 V1 同一递归链中修改：

```text
EvolutionAuthorityPolicy
Eval root / holdout
Quality/Security gate root
Release Authority
Budget Enforcement
Governance Kernel
Mutation Surface root rules
```

Strategy 不能通过“修改自己的 Mutation Constraint”来扩大可修改范围；这属于 Meta Evolution，不在 V1。

## 10. Prompt / Model Route / Context / Memory 的表达边界

V1 不因为需要调优就新增 `subject_type=prompt|context|model_route|memory_policy`。

它们默认作为版本化 Profile / Artifact 被 Agent、Skill 等引用：

```text
prompt_ref
model_route_ref
context_policy_ref
memory_policy_ref
```

例如 RAG 调参：

```text
context-policy-42
  -> R1 Mutation
  -> context-policy-43
  -> Agent.context_policy_ref 42 -> 43
```

Model temperature、max output tokens 等同理通过新 `model_route_ref` 表达；Prompt 正文通过新 `prompt_ref`；Memory ranking/TTL/consolidation 通过新 `memory_policy_ref`。

如果未来这些能力被证明具有独立生命周期、Owner、状态迁移和跨模块稳定契约，再按 Minimum Semantic Surface 重新评估是否升级。

## 11. RepairLevel 默认映射

```text
R1 Parameter / Policy
  temperature / top_k / threshold / routing weight
  context budget / timeout / retry-backoff policy

R2 Component / Route
  model route / retriever / provider / adapter
  skill/tool/component version ref

R3 Composition
  workflow topology / multi-agent composition
  verification stage / handoff structure

R4 Artifact / Code
  tool code / adapter / skill implementation
  executable strategy artifact

R5 Governance
  NEVER automatic mutation
```

该映射是默认策略，不是机械状态机。若已有强证据直接证明代码缺陷，可直接提出 R4；“证据不足”不能成为扩大 RepairLevel 的理由。

## 12. Sparse Mutation 默认限制

V1 首个实现 SHOULD 使用：

```yaml
mutation_limits:
  max_candidates: 1
  max_fields_per_candidate: 2
  max_components_per_candidate: 1
  max_scopes_per_candidate: 1
  allow_mixed_repair_levels: false
  require_single_hypothesis: true
```

闭环稳定后 MAY 扩到 2~5 个 Candidate，但仍须有 Budget 和 novelty 上限。

Candidate 默认不得同时修改多个不相关区域，例如 Prompt + Model + RAG + Workflow。否则因果归因、回归定位和失败复用都会显著变差。

## 13. Evolution Objective / Fitness Profile

### 13.1 定位

V1 不建立 `FitnessRecord` Canonical Object。Evolution Objective / Fitness Profile 是版本化 Policy/Profile，用于解释现有：

```text
EvalResult
business KPI evidence
cost / token evidence
latency / SLO evidence
complexity / fan-out evidence
security / regression evidence
```

它回答：

> 在所有通过硬约束的 Candidate 中，哪一个相对 baseline 更值得推进？

### 13.2 最小结构

```yaml
objective_profile_id: customer-support-v1
primary_objectives:
  - metric: task_success_rate
    direction: maximize
    weight: 0.6
    minimum_improvement: 0.02
  - metric: business_resolution_rate
    direction: maximize
    weight: 0.4
hard_constraints:
  security_hard_failures: 0
  cross_tenant_violation: 0
  critical_slice_regression: 0
guardrails:
  cost_per_success:
    max_regression_pct: 10
  p95_latency_ms:
    max_regression_pct: 5
  total_tokens_per_success:
    max_regression_pct: 10
  fan_out:
    max_regression_pct: 10
selection:
  method: constrained_weighted_delta
  min_evidence_confidence: 0.95
  tie_breakers: [lower_cost, lower_latency, lower_complexity]
```

业务 Owner MUST 明确至少一个可观测业务目标或完成条件。业务 KPI 到 Eval/Telemetry measurement 的映射必须版本化；无法建立可信映射时标记 `inconclusive`，不得让 LLM 自行断言业务价值提高。

### 13.3 Gate 与选择

```text
schema / contract
-> security hard constraints
-> targeted regression
-> quality / operational gates
-> objective comparison against baseline
-> candidate selection
-> release governance
```

Profile MUST 明确主目标、硬约束、允许退化项及最大区间、证据置信要求和 tie-break。禁止只保留单一 `fitness_score` 而丢失原始分项。

## 14. EvolutionStrategy Contract

### 14.1 输入

V1 Strategy MUST 只消费有界输入：

```text
EvolutionTrigger
baseline GenomeManifest
Subject Profile / Effective Mutation Surface
EvolutionAuthorityPolicy
bounded Active Working Set
Diagnosis / repair metadata
previous successful/failed attempt refs
Evolution Objective Profile
budget slice
```

不得直接扫描全量 Trace、历史数据库或未授权 Registry。

### 14.2 输出

输出为 `0..N` 个 Proposal Draft，最终规范化为既有 `MutationProposal`：

```yaml
hypothesis: string
repair_level: r1 | r2 | r3 | r4
repair_target_scope: [string]
changes: [object]
expected_gain: object
expected_cost: object
risk_refs: [string]
evidence_refs: [string]
novelty_basis_refs: [string]
```

允许 0 Candidate；这可以导致 `no_evolution_needed` 或 `no_valid_candidate`。

### 14.3 `llm_guided_sparse_mutation`

首个实现至少约束：

```text
candidate_count <= max_candidates
changed_fields <= max_fields_per_candidate
changed_components <= max_components_per_candidate
changed_scopes <= max_scopes_per_candidate
all paths machine-valid
no frozen fields
no authority expansion
no duplicate proposal without new evidence
single hypothesis required by default
expected gain/cost required
```

V1 不要求 Population/Tournament。Strategy MAY 在有限预算中做 exploit/explore，但 SHOULD 优先查询历史成功/失败 attempt refs，避免重复已知失败 Mutation。

Strategy 只能提出 Proposal，不能签发 EvalResult、修改 Gate root/Budget Enforcement，或签发 ReleaseDecision/ReleaseManifest。

## 15. 成功 Mutation 到可复用 Artifact

V1 允许把已验证局部能力沉淀成可复用资产：

```text
MutationProposal
-> GenomeManifest candidate
-> ReleaseCandidate
-> Eval / Release
-> production evidence confirms value
-> stable Profile / Policy / Skill / Tool / Workflow / Artifact
-> Registry + provenance + compatibility metadata
```

后续其他 Agent MAY 在自己的 EvolutionRun 中使用：

```text
MutationProposal(mutation_type=transfer)
-> reference registered artifact
-> target-side compatibility eval
-> normal release governance
```

V1 不包含自动 ecosystem discovery、自动跨 Agent 传播、Gene Pool 生命周期、Species/Population、Ecosystem Fitness 或跨租户自动共享。

## 16. Human-readable Mutation Review Projection

模块 11 / Developer Plane SHOULD 从现有事实生成审查 Projection：

```text
Problem
Evidence
Diagnosis
Proposed Change
Unchanged Boundaries
Why this RepairLevel
Expected Benefit
Expected Cost
Known Risks
Evaluation Plan
Canary Conditions
Rollback
Previous Attempts
Approval Requirement
```

典型说明应明确：

```text
Observed: RAG recall 87% -> 78%
Diagnosis: 新文档 slice 的 query formulation 不匹配
Repair: R1 Context Policy
Change: retrieval_top_k 5 -> 8
Not changed: Model / Prompt / Workflow / Tool / Permissions
Expected: recall +5~8%; token +6~10%; P95 latency +2~5%
Reject if: cost > +12%; critical regression > 0; security hard failure > 0
```

该 Projection 不是权威对象，每个结论必须可追溯到 Trigger、Evidence、Diagnosis、Mutation、Eval 和 Release refs。

## 17. Evolution-specific Threat Model

V1 必须显式考虑：

```text
Evidence poisoning
Delayed prompt injection through Trace/RAG/Tool payload
Trigger flooding / Evolution DoS
False novelty / repeated proposal attack
Repair-history poisoning
Eval / benchmark poisoning
Candidate artifact supply-chain attack
R4 generated code abuse
Judge manipulation
Budget exhaustion
Privilege escalation disguised as repair
```

Evidence Expansion 的自由文本/payload 必须视为不可信数据，与 Strategy/Judge 指令结构隔离，并保留 provenance/source refs。R4 Candidate 必须经过 artifact integrity、static analysis、unit/integration、sandbox、SBOM/dependency、secret scanning、permission diff、security regression、compatibility 和 risk-based canary。

模块 09 SHOULD 观察 Evolution 自身结构化 meta-metrics，如 trigger 转化率、`no_evolution_needed`、candidate rejection/regression/safety block、rollback、成本、重复提案、novelty rejection、Evidence Expansion 用量和 time-to-terminal；不建设递归“AI 监控 AI”系统。

## 18. Evolution Success Definition

一次 EvolutionRun 只有在以下条件全部满足时才 MAY 以 `improved` 结束：

1. 至少一个 Candidate 通过 RepairLevel 所需硬门禁；
2. 相对 baseline 满足 Objective Profile 的主目标/最小改善；
3. 所有 hard constraints 通过；
4. 允许退化项均处于 guardrail；
5. Evidence confidence 达到最低要求；
6. Candidate 可追溯到 Trigger、Diagnosis、Mutation、Genome、Eval；
7. `improved` 只表示找到更优候选，不表示已生产发布。

Canary/Production 若回归，应形成新的 Evidence，不得重写历史 EvalResult 来维持“进化成功”。

## 19. V1 验收条件

1. 五类 Subject 均有明确 mutable/bounded/replace-only/conditional/frozen 操作面；
2. 任意 Mutation path 都可由 Subject Profile 机器校验；
3. Effective Mutation Surface 是 Profile、Authority、Run scope、Repair target、risk profile 的交集；
4. 未声明 mutable 的字段无法进入 Candidate；
5. frozen/Governance 字段无法通过 Strategy 或自由 JSON 绕过；
6. Agent 默认只持组合引用和少量 bounded 行为，不重复拥有底层组件细节；
7. Tool timeout/unknown 仍先 reconciliation，Tool 权限不会因失败自动扩大；
8. Workflow mandatory approval/security/reconciliation 节点无法因成本或延迟被自动删除；
9. Strategy 不能修改 Mutation root、Eval root、Budget Enforcement 或 Release Authority；
10. Prompt/Context/Memory/Model Route 在 V1 作为版本化 Profile/Artifact 表达，不新增 subject_type；
11. Candidate 选择可还原到现有 EvalResult 与版本化 Objective Profile；
12. 多目标 trade-off 有 hard constraint / guardrail / tie-break；
13. `llm_guided_sparse_mutation` 有稳定输入输出、Candidate/field/component/scope 上限；
14. 首个实现默认单一 hypothesis、单一 repair target、最多 1 Candidate、1 component、1~2 fields；
15. 成功能力可沉淀到既有 Registry/Artifact 并由其他 Agent 通过普通 Mutation 复用；
16. 未建设 Gene Pool、Species、Ecosystem Fitness 或自动传播服务；
17. Mutation Review 可生成人类可读、可追溯解释；
18. Evolution 链具备专门威胁模型与自身健康指标；
19. 未新增第六个 Evolution Canonical Object。
