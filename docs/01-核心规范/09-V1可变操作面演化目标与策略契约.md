# UEAF V1 可变操作面、演化目标与策略契约

版本：`0.1.0-draft`  
规范状态：Draft  
Architecture Generation: `V1`  
Maturity: `Required`  
Implementation: `Current`

## 1. 范围

本文补齐 UEAF V1 Controlled Evolution Kernel 的三个执行缺口：

1. **进化什么**：把 `GenomeManifest.profile_ref` 解析为机器可验证的可变操作面；
2. **怎样算更好**：通过版本化 Evolution Objective / Fitness Profile 解释既有 `EvalResult`，形成候选相对基线的选择规则；
3. **怎样搜索**：定义 `EvolutionStrategy` 的最小输入、输出、预算和候选生成约束。

本文不新增第六个 Evolution Canonical Object，也不建设独立 GeneSpace、Fitness、Experiment 或 Strategy Domain。

所有表达复用：

```text
GenomeManifest.profile_ref
Registry metadata / versioned Profile
EvolutionAuthorityPolicy
MutationProposal
EvalConfig / EvalResult / Gate
BudgetEnvelope / Budget Ledger
ReleaseCandidate / ReleaseManifest
```

## 2. 核心原则

1. **Mutable Scope 必须继续下钻到 Mutable Field。** `mutable_scope=[context_policy]` 不能直接授权任意 JSON 修改。
2. **每个 Mutation 必须先通过机器校验，再进入 Candidate Build。** LLM 不能通过自由 `change_summary` 绕过字段、范围、类型或跨字段约束。
3. **Fitness 不是新的真相源。** 选择结果必须可还原到现有 `EvalResult`、成本、延迟、安全与业务 KPI 证据。
4. **Gate 与 Optimization Objective 分离。** Gate 回答“能否接受”，Objective 回答“在可接受候选中哪个更值得推进”。
5. **安全与治理硬约束不可被权重抵消。** 任何安全硬失败、权限越界、治理边界违规都不能因业务收益较高而通过加权总分覆盖。
6. **Sparse Mutation 必须可度量。** 单次候选最多修改多少字段、多少组件、多少 scope 必须由 Profile/Strategy Policy 明确约束。
7. **搜索预算有界。** Candidate 数、模型调用、Token、金额、wall time、重复尝试和强模型调用均受既有 Budget 约束。
8. **V1 不做生态级自动传播。** 成功能力可以沉淀为版本化 Artifact 并由其他 Agent 后续通过普通 Mutation 复用，但自动发现/传播/Gene Pool 属于 V2。

## 3. V1 Mutable Field Contract

### 3.1 定位

`GenomeManifest.profile_ref` MUST 指向一个版本化 Subject Profile。该 Profile 除定义必需组件和兼容规则外，还必须定义本 Subject 的 **Mutation Surface Contract**。

它不是新的 Canonical Object；可作为 Registry 中受版本控制的 Profile/metadata 保存。

推荐结构：

```yaml
profile_id: agent-standard-v1
subject_type: agent
schema_version: 1
mutable_fields:
  - path: prompt.template_ref
    type: ref
    operations: [replace]
    allowed_registry: prompt
  - path: model.route_ref
    type: ref
    operations: [replace]
    allowed_registry: model_route
  - path: model.temperature
    type: number
    operations: [replace]
    min: 0.0
    max: 1.2
  - path: context.retrieval_top_k
    type: integer
    operations: [replace]
    min: 1
    max: 20
  - path: context.max_tokens
    type: integer
    operations: [replace]
    min: 512
    max: 16000
frozen_fields:
  - identity.*
  - permissions.*
  - release_authority.*
  - eval_root.*
  - budget_enforcement.*
cross_field_constraints:
  - "context.max_tokens <= model.route.max_context_tokens"
  - "context.retrieval_top_k >= 1"
mutation_limits:
  max_fields_per_candidate: 2
  max_components_per_candidate: 1
```

### 3.2 字段规则

每个 `mutable_fields[]` SHOULD 至少描述：

```text
path
value type
allowed operations
range / enum / registry constraint
required compatibility checks
risk class
```

MAY 额外描述：

```text
default value
step size
semantic tags
dependencies
mutual exclusion
requires canary
requires human review
```

### 3.3 Frozen Field

`frozen_fields` 用于表达当前 Subject/Profile 下不可被同一 EvolutionRun 修改的字段。

Governance Kernel 无论 Profile 如何配置都必须保持冻结；普通企业配置不能把以下内容改成可变：

```text
Identity / Delegation root
Permission / PDP / PEP
Tool Gateway enforcement
Secrets / Credentials
Audit root
Eval root / holdout / threshold root
Release Authority
Budget Enforcement
Kill switch / Legal Hold / Deletion root
```

### 3.4 MutationProposal 机器可验证化

`MutationProposal.change_summary` 仍保留人类可读摘要，但 SHOULD 增加机器可验证的 `changes` 字段：

```yaml
changes:
  - path: context.retrieval_top_k
    operation: replace
    before: 5
    after: 8
    constraint_profile_ref: agent-standard-v1
```

每条 change MUST 满足：

```text
path ∈ profile.mutable_fields
operation ∈ allowed_operations
new value satisfies type/range/enum/ref constraints
path ∈ EvolutionRun.mutable_scope
path allowed by EvolutionAuthorityPolicy
cross-field constraints remain valid
frozen field not touched
```

任一条件失败，Candidate Build MUST 拒绝，不允许由 LLM 解释为“意图正确所以继续”。

### 3.5 subject_type 最小 V1 操作面

以下是 V1 最小推荐集合，不要求所有部署同时开放。

#### agent

```text
prompt template/version ref
model route ref
model generation parameters
context/retrieval policy refs and bounded parameters
memory policy ref / bounded retrieval-write parameters
workflow ref
approved capability refs
```

#### skill

```text
skill prompt/instruction artifact ref
input/output schema-compatible config
approved tool/model/context dependencies
implementation artifact ref (R4 only)
```

#### tool

```text
adapter/provider version ref
timeout/polling/backoff bounded config
schema-compatible mapping
implementation artifact ref (R4 only)
```

工具权限、凭据和 Tool Gateway enforcement 不属于可变字段。

#### workflow

```text
node component refs
bounded branch/routing parameters
stop/retry policy
node ordering/topology (R3)
verification/merge strategy refs
```

#### strategy

```text
strategy implementation ref
search hyperparameters
candidate limits
exploration policy within V1 budget
```

Strategy 不得修改自身 Budget Enforcement、Eval root 或 Release Authority。

## 4. Evolution Objective / Fitness Profile

### 4.1 定位

V1 不建立 `FitnessRecord` Canonical Object。

Evolution Objective / Fitness Profile 是版本化 Policy/Profile，用于解释现有：

```text
EvalResult
business KPI evidence
cost / token evidence
latency / SLO evidence
complexity / fan-out evidence
security / regression evidence
```

它回答：

> 在所有通过硬约束的 Candidate 中，哪一个相对 baseline 更值得推进？

### 4.2 最小结构

```yaml
objective_profile_id: customer-support-v1
primary_objectives:
  - metric: task_success_rate
    direction: maximize
    weight: 0.6
    minimum_improvement: 0.02
  - metric: business_resolution_rate
    direction: maximize
    weight: 0.4
hard_constraints:
  security_hard_failures: 0
  cross_tenant_violation: 0
  critical_slice_regression: 0
guardrails:
  cost_per_success:
    max_regression_pct: 10
  p95_latency_ms:
    max_regression_pct: 5
  total_tokens_per_success:
    max_regression_pct: 10
  fan_out:
    max_regression_pct: 10
selection:
  method: constrained_weighted_delta
  min_evidence_confidence: 0.95
  tie_breakers:
    - lower_cost
    - lower_latency
    - lower_complexity
```

### 4.3 业务 KPI 与技术指标映射

业务 Owner MUST 明确至少一个可观测业务目标或完成条件。

Profile SHOULD 保存从业务 KPI 到 Eval/Telemetry measurement 的映射，例如：

```yaml
business_metric_mapping:
  business_resolution_rate:
    source: eval_slice
    ref: support-resolution-v3
  customer_escalation_rate:
    source: production_metric
    ref: metric://support/escalation_rate
```

若无法建立可信映射，应将该目标标记为 `inconclusive`，不得让 LLM 自行推断“客户满意度一定提高”。

### 4.4 Gate 与选择顺序

推荐顺序：

```text
Candidate
  -> hard schema / contract checks
  -> security hard constraints
  -> targeted regression gates
  -> quality / operational gates
  -> objective comparison against baseline
  -> candidate selection
  -> release governance
```

任何 hard constraint failure 都先于加权优化。

### 4.5 Trade-off 规则

Profile MUST 明确：

- 哪些指标是主目标；
- 哪些是硬约束；
- 哪些允许有限退化；
- 每个可退化指标最大可接受区间；
- 如何处理不确定性和证据不足；
- 平分候选如何 tie-break。

禁止只有一个模糊 `fitness_score` 而不保留原始分项。

## 5. EvolutionStrategy Contract

### 5.1 输入

V1 Strategy MUST 只消费有界输入：

```text
EvolutionTrigger
baseline GenomeManifest
Subject Profile / Mutation Surface Contract
EvolutionAuthorityPolicy
bounded Active Working Set
Diagnosis / repair metadata
previous successful/failed attempt refs
Evolution Objective Profile
budget slice
```

Strategy 不得直接扫描全量 Trace、历史数据库或未授权 Registry。

### 5.2 输出

Strategy 输出为 0..N 个 Proposal Draft，最终规范化为既有 `MutationProposal`。

每个 Proposal 至少包含：

```yaml
hypothesis: string
repair_level: r1 | r2 | r3 | r4
repair_target_scope: [string]
changes: [object]
expected_gain: object
expected_cost: object
risk_refs: [string]
evidence_refs: [string]
novelty_basis_refs: [string]
```

允许输出 0 个候选；这可以导致 `no_evolution_needed` 或 `no_valid_candidate`。

### 5.3 llm_guided_sparse_mutation 最小规则

V1 默认 Strategy SHOULD 先实现 `llm_guided_sparse_mutation`。

最小约束：

```text
candidate_count <= strategy.max_candidates
changed_fields_per_candidate <= profile.max_fields_per_candidate
changed_components_per_candidate <= profile.max_components_per_candidate
all paths machine-valid
no frozen fields
no authority expansion
no duplicated proposal without new evidence
hypothesis required
expected gain/cost required
```

推荐首个闭环：

```text
max_candidates = 1
max_fields_per_candidate = 1..2
```

闭环稳定后再允许 2~5 个 Candidate。

### 5.4 Exploration / Exploitation

V1 不要求 Population/Tournament。

有限候选情况下，Strategy MAY 将预算分为：

```text
exploit: 优先复用已验证成功的相似修复
explore: 在 novelty 足够时尝试一个新候选
```

默认 SHOULD 先查询 previous attempt refs，避免重复已知失败 Mutation。

### 5.5 Strategy 不拥有发布权

Strategy 只能提出 Proposal；不能：

```text
签发 EvalResult
修改 Gate threshold root
修改 Budget Enforcement
签发 ReleaseDecision
签发 ReleaseManifest
```

## 6. 成功 Mutation 到可复用 Artifact

V1 允许把已验证的局部能力沉淀成可复用资产，但不建设 V2 Gene Pool。

推荐闭环：

```text
MutationProposal
  -> GenomeManifest candidate
  -> ReleaseCandidate
  -> Eval / Release
  -> production evidence confirms value
  -> extract stable capability/config/artifact
  -> register versioned Artifact / Profile / Policy / Skill / Tool / Workflow
  -> attach provenance + compatibility metadata
```

后续其他 Agent MAY 在自己的 EvolutionRun 中：

```text
MutationProposal(mutation_type=transfer)
  -> reference registered artifact
  -> target-side compatibility eval
  -> normal release governance
```

V1 明确不包含：

```text
automatic ecosystem discovery
automatic cross-agent propagation
Gene Pool lifecycle
Species / Population
Ecosystem Fitness
cross-tenant automatic sharing
```

跨租户复用必须经过正常发布、数据与安全治理。

## 7. Human-readable Mutation Review Projection

企业审查者不应被迫阅读原始 Trace、JSON diff 或模型内部推理。

模块 11 / Developer Plane SHOULD 能从现有对象生成以下人类可读 Projection：

```text
Problem
  发生了什么，影响哪个业务/切片

Evidence
  样本量、时间窗、baseline、关键 refs

Diagnosis
  observed scope / likely root cause / confidence

Proposed Change
  改哪些字段，before -> after

Unchanged Boundaries
  明确哪些权限、工具、workflow、治理字段未改

Expected Benefit
  目标 KPI / quality / cost / latency 预期变化

Known Risks
  回归、安全、复杂度和证据不确定性

Evaluation Plan
  targeted eval / compatibility / canary / hard gates

Rollback
  baseline release / rollback target

Previous Attempts
  已成功/失败的相关 Proposal refs

Approval Requirement
  automatic_after_gates | canary | gated | never
```

该 Projection 不是新的权威对象；其每个结论必须可回溯到 `MutationProposal`、Evidence、Eval 与 Release refs。

## 8. Evolution-specific Threat Model

### 8.1 主要攻击面

V1 必须显式考虑：

```text
Evidence poisoning
Delayed prompt injection through Trace/RAG/Tool payload
Trigger flooding / Evolution DoS
False novelty / repeated proposal attack
Repair-history poisoning
Eval / benchmark poisoning
Candidate artifact supply-chain attack
R4 generated code abuse
Judge manipulation
Budget exhaustion
Privilege escalation disguised as repair
```

### 8.2 Evidence 污染

Evidence Expansion 读取的文本或 payload MUST 视为不可信数据，而不是系统指令。

进入 Evolution Model 前 SHOULD：

- 保留 provenance/source refs；
- 标记 user/model/tool/system-origin；
- 对高风险自由文本做注入/恶意指令检测；
- 将原始数据与 Strategy/Judge 指令进行结构隔离；
- 对单一来源设置影响上限；
- 使用 A/B/C 对照避免由单一异常样本驱动 Mutation。

### 8.3 Candidate / R4 安全

R4 Candidate MUST 继续经过模块 10/08/07 既有机制，并至少包含：

```text
artifact integrity / provenance
static analysis
unit/integration tests
sandbox execution
dependency/SBOM checks
secret scanning
permission/capability diff
security regression
compatibility tests
risk-based canary
```

生成代码不得直接写生产仓库或生产环境。

### 8.4 Evolution Health Meta-metrics

模块 09 SHOULD 观察 Evolution Kernel 自身健康，但不使用“另一个 LLM 持续监控 Evolution LLM”。

推荐指标：

```text
trigger_candidate_count
trigger_count
trigger_candidate_to_trigger_rate
no_evolution_needed_rate
no_valid_candidate_rate
candidate_rejection_rate
candidate_regression_rate
candidate_safety_block_rate
rollback_rate_after_evolution
median_evolution_cost
strong_model_calls_per_evolution
repeat_proposal_rate
novelty_rejection_rate
evidence_expansion_bytes/tokens
time_to_terminal
```

异常阈值由普通 SRE/Security/Eval 机制处理；Evolution Kernel 不递归修改自身 Governance Kernel。

## 9. V1 Evolution Success Definition

一次 EvolutionRun 只有在以下条件全部满足时，才 MAY 以 `improved` 结束：

1. 至少一个 Candidate 通过其 Repair Level 所需的硬门禁；
2. 相对 baseline 满足 Objective Profile 的主目标/最小改善要求；
3. 所有 hard constraints 通过；
4. 允许退化项均处于 Profile 明确的 guardrail 区间；
5. Evidence confidence 达到最低要求；
6. Candidate 可追溯到 Trigger、Diagnosis、Mutation、Genome、Eval；
7. `improved` 仅表示“找到了更优候选”，不表示已经发布生产。

生产上线后若 Canary/Production 反馈回归，应形成新的 Evidence；不得修改历史 EvalResult 以维持“进化成功”的叙事。

## 10. V1 验收条件

1. 任意 Mutation 的每个 path 都可由 Subject Profile 机器校验；
2. 未声明 mutable 的字段无法进入 Candidate；
3. frozen/Governance 字段无法通过 Strategy 或自由 JSON 绕过；
4. Candidate 选择可还原到现有 EvalResult 与版本化 Objective Profile；
5. 多目标 trade-off 有明确 hard constraint / guardrail / tie-break；
6. `llm_guided_sparse_mutation` 有稳定输入输出、候选数和字段数上限；
7. Strategy 可以返回 0 Candidate；
8. 成功能力可沉淀到既有 Registry/Artifact 并由其他 Agent 通过普通 Mutation 复用；
9. 未建设 Gene Pool、Species、Ecosystem Fitness 或自动传播服务；
10. Mutation Review 可生成人类可读、可追溯的解释；
11. Evidence/Mutation/R4 Candidate 具备 Evolution-specific 威胁模型与安全检查；
12. Evolution 自身健康指标可由普通 Telemetry/SRE 观察；
13. 未新增第六个 Evolution Canonical Object。
