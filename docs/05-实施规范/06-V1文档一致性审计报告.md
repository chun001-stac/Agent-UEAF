# UEAF V1 文档一致性审计报告

初次审计日期：`2026-08-14`
纠偏复核日期：`2026-08-15`
审计范围：`main` 当前 V1 文档
Architecture Generation: `V1`
状态：`Corrective Revalidation Complete / Conditional Development Gate`

## 1. 审计目标

本次审计不再讨论 UEAF 是否需要新的架构概念，而是回答：

> 把当前 `main` 交给 Codex 后，是否仍存在会让它生成两套对象、两套状态、两套 Port、错误事件名或错误事务顺序的文档冲突？

审计按以下优先级执行：

```text
核心规范
> 总体设计
> ADR
> 功能模块
> 实施规范
> 参考架构
```

分级：

```text
P0  会导致错误 Canonical Schema / 状态 / 权威边界 / 关键事务
P1  会导致不同实现者选择不同公共接口或 Reference Profile
P2  示例、历史措辞或低优先级参考债，不覆盖当前机器契约
```

## 3. P0 已发现并修复

### AUD-P0-001 README 文档优先级缺实施层

**问题**：README 旧优先级没有 `实施规范`，与 `AGENTS.md/docs/05` 冲突。

**修复**：README 统一为：

```text
核心规范
> 总体设计
> ADR
> 功能模块
> 实施规范
> 参考架构
```

并加入实施规范/Codex 开工入口。

### AUD-P0-002 总体设计遗漏 Module 11

**问题**：高优先级总体设计仍只有 01–10，可能让 Codex 将 Controlled Evolution 排除 V1。

**修复**：总体设计重写为 Current V1 11 模块，Module 11 明确属于 Reference Implementation/验收。

### AUD-P0-003 第二套 `EventEnvelope`

**问题**：早期实施文档定义简化 Event Envelope：

```text
event_type / aggregate_ref / revision / correlation_refs
```

与核心完整 EventEnvelope 冲突。

**修复**：Machine Schema、API/Event 实施规范、总体设计/模块全景全部直接复用核心 EventEnvelope：

```text
event_id
event_name
event_version
occurred_at
recorded_at
tenant_id
aggregate_type
aggregate_id
aggregate_version
sequence
producer
producer_version
correlation_id
causation_id
trace_id
principal_ref
release_id
payload_schema_ref
payload
classification
purpose
integrity_ref when required
```

### AUD-P0-004 public event 命名漂移

**问题**：实施/总览曾使用 `TaskQueued/EvolutionTriggerCreated/...` 等 PascalCase 或提前注册 `ueaf.evolution.*`。

**修复**：公共 event 只允许核心已注册；残留的 `RunQueued` 已统一为 `ueaf.run.created`：

```text
ueaf.<domain>.<past_tense_fact>
```

当前 Evolution lifecycle event 未进入核心事件目录时，只允许 Module 11 internal event/attempt metadata。需要跨进程 public event 时必须先更新核心事件规范/ADR。

### AUD-P0-005 RuntimeAdapter 双 SPI

**问题**：核心规范与 Module 10/实施规范曾存在两套必需方法。

**修复**：唯一最小 SPI：

```text
DescribeRuntime
StartRun
AdvanceRun
SuspendRun
ResumeRun
CancelRun
InspectRun
```

公共接口名只允许 `RuntimeAdapter`；`RuntimeAdapterPort` 不再作为第二公共名。`ValidateRelease/StreamEvents/Snapshot/Close` 仅 optional/private convenience。

### AUD-P0-006 Context/Telemetry Port 同名不同义

**问题**：存在 `ContextPort`、`TelemetryPort.emit(TelemetryEvent)` 等与核心端口不同签名的表达。

**修复**：统一：

```text
ContextBuildPort
ModelStepPort
ToolIntentPort
HandoffPort
TelemetryPort:
  EmitTrace
  EmitMetric
  EmitLog
  EmitAudit
```

模块内部可有私有 non-blocking buffer，但不能使用同一公共 Port 名建立第二接口。

### AUD-P0-007 `ErrorEnvelope` 术语漂移

**问题**：ADR-002/Module 01 早期使用 `ErrorEnvelope`，核心规范已拆成更精确错误契约。

**修复**：

```text
API/cross-process -> ProblemDetail
Port              -> PortResult<T> / PortError
RunRecord          -> error_ref
```

新代码/Schema 禁止公共 `ErrorEnvelope`。

### AUD-P0-008 `ContractMeta` 被下层示例省略

**问题**：核心要求所有跨模块持久化对象有 `meta: ContractMeta`，后续领域 YAML 常只列领域字段，Machine Schema 原先未明确继承关系。

**修复**：Machine Schema/README/AGENTS 明确：

```text
persistent canonical object
= ContractMeta + domain fields
```

并要求对象领域 ID 与 `meta.object_id` 一致。

### AUD-P0-009 第二套 `PrincipalContext`

**问题**：Module 07 曾以 `subject_id/identity_provider/assurance_level/...` 重新定义同名 `PrincipalContext`。

**修复**：Module 01/07 统一到核心：

```text
principal_id
principal_type
tenant_id
roles
scopes
delegation_chain
authentication_strength
credential_ref
data_regions
consent_refs
issued_at
expires_at
revocation_ref
meta
```

顶层 `tenant_id` 是 MUST 且 MUST 等于 `meta.tenant_id`，不是可选镜像。额外 IdP/workload/assurance 观察使用已有字段、namespaced extension 或受控 evidence ref。

### AUD-P0-010 `R0..R3` 风险与 RepairLevel 符号碰撞

**问题**：Task risk 曾用 `R0/R1/R2/R3`，Evolution Repair Ladder 也使用 `R0..R5`，语义完全不同。

**修复**：新 `TaskEnvelope.risk_class`：

```text
compute_only
read_only
reversible_write
high_risk_write
```

旧任务风险 `R0..R3` 仅 deprecated migration alias。Evolution RepairLevel 的概念标签为 `R0..R5`，wire/Schema/config 值为 `r0..r5`；`MutationProposal.repair_level` 只允许 `r1..r4`。

### AUD-P0-011 `ReleaseManifest` 单数/复数字段冲突

**问题**：核心是版本集合，Module 08 曾写单数 Agent/Prompt/Schema/ModelRoute。

**修复**：统一线级字段：

```text
agent_versions
prompt_versions
schema_versions
model_route_versions
capability_versions
adapter_versions
knowledge_index_versions
memory_policy_versions
policy_versions
```

单 Agent Profile 可用 `maxItems=1`，不能改字段名。

### AUD-P0-012 Evolution 构建跳过 Genome

**问题**：部分实施/全景表述可读成 `MutationProposal -> ReleaseCandidate`。

**修复**：固定：

```text
MutationProposal
-> machine validation
-> GenomeManifest candidate
-> Module 10 ReleaseCandidate
-> Eval / Gates / Release
```

Genome materialization 属于 Module 11/Genome owner 应用操作，不新增 Canonical Object/服务。

### AUD-P0-013 Action transaction 顺序漂移

**问题**：旧持久化实施稿可解释为 PDP/Approval 后才首次创建 action_key/ActionRecord，与 Module 05 当前动作身份语义冲突。

**修复**：

```text
server-side canonicalize
-> stable action_fingerprint + action_key
-> ActionRecord(proposed)
-> validation / PDP / Approval
-> reserve existing identity
-> external execution
-> receipt / unknown / reconciliation
```

动作身份在 Policy 前稳定；side effect 在 allow/approval/reservation 后发生。

### AUD-P0-014 Runtime Adapter 冻结时点漂移

**问题**：Module 02 曾在 Run admission 通过后才选择 Runtime Adapter，与创建 `RunRecord(queued)` 时冻结 `runtime_adapter_ref` 的核心顺序冲突。

**修复**：在创建 Run 前按 Release、任务、环境、区域和能力选择精确 Adapter/CapabilityBinding；创建 Run 时冻结引用。Admission 校验该冻结引用，admitted 后只复核，不得重选或静默切换。

### AUD-P0-015 Outbox 强度被放宽

**问题**：实施规范 02 曾把核心 transactional outbox 的 `MUST` 写为 `SHOULD`。

**修复**：权威 DB transaction 与 Event publish 恢复为 `MUST` 使用 transactional outbox、同一事务日志或可证明等价机制。

### AUD-P0-016 Repair Router 输出闭集不一致

**问题**：核心规范一处写三类输出，Governance 边界和下层文档写四类输出。

**修复**：唯一闭集为：

```text
NO_EVOLUTION
OPERATIONAL_ONLY
MUTATION
ROUTE_GOVERNANCE
```

`ROUTE_GOVERNANCE` 对应概念 R5/wire `r5`，不得生成 `MutationProposal`；`MUTATION` 只允许 `r1..r4`。

## 4. P1 已发现并修复

### AUD-P1-001 Evolution “可选 Profile”歧义


```text

```

这些不改变 UEAF 的供应商无关契约。

### AUD-P1-003 Module 10 “支持五个 Runtime”验收过重

已收敛为：LangGraph + Reference Adapter #2 必须有真实 Conformance；MAF/ADK/CrewAI 等可保留映射设计，按后续需求进入 Backlog。

### AUD-P1-004 Evolution Canonical Subject 漏 `strategy`

产品成功标准和 Mutation Surface 已统一为：

```text
agent | skill | tool | workflow | strategy
```

### AUD-P1-005 Adapter 描述对象命名漂移

总体整合策略中的 `AdapterCapabilityDescriptor` 已统一为核心 `AdapterDescriptor`，避免 Registry/SDK 生成第二描述类型。

### AUD-P1-006 实施阶段与 Test ID owner 歧义

Phase 2 明确只交付 non-Eval runtime smoke；Phase 4 才交付冻结 EvaluationBundle 到 QualityGateDecision 的 read-only Eval vertical slice。实施规范 04 是 Test ID 前缀注册表，并且是 `P0-SCH-*`/`P0-PORT-*` 的唯一具体 ID 与 expected-semantics Owner；实施规范 08 对这两类只补充 fixture/执行说明。

## 5. P2 剩余非阻塞债

以下仍可能在低优先级历史/参考文字中看到，但不会覆盖当前实现契约：

### P2-01 功能模块中的公共 meta 简写

Module 03/04 等部分段落用“tenant/trace/correlation/integrity”等文字概括公共字段。实现 MUST 使用核心 `ContractMeta`；这些段落只作为领域说明，不是第二 Machine Schema。

### P2-02 参考存储产品示例

`03-参考架构/03-数据存储与一致性.md` 仍以 Kafka/云消息服务作为通用事件传输示例。首个 Reference Implementation 已由更高优先级实施规范固定 NATS JetStream；参考文档只表示 broker 可替换。

### P2-03 90 天路线方法名简写

MVP 路线中可能出现 `start/stream/cancel`、`non-blocking TelemetryPort` 等自然语言简写。真正接口以核心 Port + 实施规范 02 为准，不用于代码生成。

### P2-04 参考层旧物理字段示例

部分参考表使用旧或简化 Action/Event 存储列。实际 Migration/ORM 应以实施规范 03 + Machine Schema 为准。

这些 P2 不构成阻塞，但后续修改相关文件时 SHOULD 顺手同步，不需要为了消除文字差异重新设计架构。

## 8. Code-readiness 结论

### Documentation Contract Convergence

**PASS（2026-08-15 纠偏复核后）**。

本结论只表示当前文档不再需要新的架构发散，并且本轮已知 P0 文档冲突已收敛；它不等于代码、Schema、Migration、测试或 CI 已满足 Definition of Done。

### V1 Development Gate

结论为 **CONDITIONAL-GO**：可以按 Phase 顺序开发，但每一阶段必须先把对应规范机器化并通过相关 CON/domain Test IDs。特别是：

```text
Phase 1 -> Principal/Admission/Run/Event/Outbox contracts and tests
Phase 2 -> non-Eval runtime smoke only
Phase 3 -> Action identity/Policy/Approval/Reservation/Reconciliation
Phase 4 -> read-only Eval vertical slice + Release authority separation
Phase 5/6 -> Evidence and Controlled Evolution with RepairLevel wire rules
```

若机器化或测试中发现新的跨文档语义矛盾，必须按 AGENTS.md 停止扩大受影响代码并先回文档/ADR。未经相关测试验证，不得把本报告的 Documentation PASS 表述为 Full Implementation Ready。

## 9. 建议冻结点

从本报告起，V1 建议进入：

```text
Architecture Feature Freeze
```

含义：

- 不再主动新增 V1 Canonical Object、模块、服务、状态机；
- 后续文档变更优先是机器化澄清、缺陷修复和实现反馈；
- 新架构能力只有在当前对象确实无法表达时才通过 ADR 重开设计；
- V2/V3 继续保持 Future/Research。

这不是禁止修文档，而是从“架构设计阶段”切换到“契约实现与验证阶段”。
