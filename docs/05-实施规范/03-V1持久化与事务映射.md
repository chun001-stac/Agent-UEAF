# UEAF V1 持久化与事务映射规范

版本：`0.1.0-draft`  
规范状态：Draft  
Architecture Generation: `V1`  
Maturity: `Required for Implementation`  
Implementation: `Current`

## 1. 目的

本文定义 V1 语义对象、Projection、Telemetry、Artifact 与物理存储之间的参考映射，并规定事务、CAS、fencing、outbox、幂等和租户隔离边界。

原则：**Semantic Owner 决定事实语义；物理数据库不获得第二语义所有权。**

## 2. 参考物理组件

V1 Reference Implementation 推荐最少使用：

```text
PostgreSQL or equivalent relational store
Persistent queue / broker
OpenTelemetry-compatible observability backend
Object storage / artifact store
Secret store
```

不要求 Evolution 专用 Vector DB、Graph DB、TSDB 或 GenePool DB。

## 3. PostgreSQL 逻辑 Schema

建议按逻辑模块分 schema 或 table prefix，而不是按未来微服务预拆数据库：

```text
core_*        task/run/state/outbox
context_*     manifests/registry refs
model_*       invocation summaries/route metadata
 action_*     actions/attempts/receipts/approvals
workflow_*    workflow run/node projections where required
security_*    policy refs/decision refs where permitted
 eval_*       eval configs/runs/results/gates
release_*     candidates/decisions/manifests
evolution_*   V1 five canonical objects
projection_*  summaries/windows/fingerprints/read models
```

Audit/Trace/Log 不因方便被塞入普通业务表成为长期权威存储。

## 4. Authoritative Table 最小集合

### 4.1 Core

```text
task_states
run_records
run_admission_results
checkpoints metadata/refs
```

### 4.2 Action

```text
action_records
execution_attempts
action_receipts
approval_requests
```

### 4.3 Eval / Release

```text
release_candidates
eval_configs
eval_runs
eval_results
quality_gate_decisions
release_decisions
release_manifests
```

Security/Operational decisions 可由其语义模块拥有独立表或受控存储，但 Release 只保存稳定引用。

### 4.4 Evolution

V1 仅：

```text
evolution_triggers
evolution_runs
genome_manifests
mutation_proposals
evolution_authority_policies
```

禁止额外建立：

```text
fitness_records
gene_spaces
repair_history_authority
lineage_authority
evolution_budget_ledger
```

## 5. Projection Table

以下 MAY 物化，但不是第二真相源：

```text
run_summaries
rolling_aggregate_windows
error_fingerprints
trigger_candidate_views
fitness_comparison_views
lineage_views
repair_history_views
mutation_review_views
```

Projection 必须保存 source refs / rebuild marker / projection version；允许删除重建。

## 6. Primary Key / Tenant / Revision

所有 tenant-scoped authoritative row SHOULD 至少包含：

```text
id
 tenant_id
revision
created_at
updated_at
```

不可变对象如 `GenomeManifest` / `ReleaseManifest` MAY 采用 append-only，不允许原地修改内容；状态变化通过生命周期字段/事件或新对象表达。

高风险表查询必须把 `tenant_id` 作为强制过滤条件或使用数据库级隔离策略。

## 7. Ref 与 Foreign Key

跨 Domain `*_ref` 是否使用数据库 FK 取决于部署边界，但语义上必须验证引用存在性/版本兼容性。

同一事务域内 SHOULD 使用 FK/unique/check constraint 保护明显不变量；跨域不得为了 FK 强绑定破坏模块边界。

## 8. Run State Transaction

Run 状态推进使用：

```text
BEGIN
  SELECT current revision
  verify expected phase/revision
  UPDATE run_records ... revision = revision + 1
  INSERT outbox event
COMMIT
```

禁止：

```text
read state
external call
blind UPDATE without revision guard
```

## 9. CAS / Fencing

Coordinator/Worker 对可恢复 Run MUST 使用 lease + fencing token 或等价机制。

规则：

```text
new lease -> larger fencing_token
write/checkpoint/action attempt carries token
stale token -> reject
```

旧 Worker 即使网络恢复也不能覆盖新 Worker 已提交状态。

## 10. Action Transaction Boundary

高风险副作用必须先有 durable `ActionRecord` / reservation，再执行外部写操作。

参考顺序：

```text
TX1:
  validate intent/policy/approval
  reserve action_key
  create ActionRecord
  outbox ActionReserved
COMMIT

external call

TX2:
  create ExecutionAttempt / Receipt or outcome_unknown
  update ActionRecord by revision
  outbox domain event
COMMIT
```

不能把数据库事务跨越不可控的远程 API 调用。

## 11. Action Idempotency

`action_key` MUST 有唯一约束，至少包含能稳定识别业务动作的语义输入摘要。

若执行超时且 `outcome_certainty=unknown`：

```text
ActionRecord -> reconciling
```

在 authoritative reconciliation 前不得创建不同 action_key 进行同义重试。

## 12. Evolution Transaction

### Trigger

`EvolutionTrigger` 形成时，应在同一事务中保存：

```text
trigger row
threshold/profile/version refs
gate evidence refs
outbox EvolutionTriggerCreated
```

### EvolutionRun

创建时固定：

```text
trigger_ref
baseline_genome_ref
budget_ref
mutable_scope
strategy_ref
active_working_set_ref
```

这些基线引用不能在运行中静默切换。

### Mutation

`MutationProposal` append-only；若 Proposal 修订，使用新 proposal/version/attempt metadata，不覆盖历史提案内容。

## 13. Genome / Artifact

`GenomeManifest` 是不可变引用图。内容变化必须新建 `genome_id`。

大型 Prompt、代码、Workflow bundle、SBOM、Trace Payload 不复制进入 Genome 表；只保存 registry/artifact refs 和 integrity refs。

## 14. Eval / Release Transaction

`EvalResult` 追加写，重跑产生新结果，不能覆盖旧评分。

`ReleaseDecision` 与 `ReleaseManifest` 必须引用冻结后的 candidate/evidence/gate 版本。

Manifest signing 前验证：

```text
all required decision refs active
same candidate/environment
integrity refs valid
rollback target present where required
```

## 15. Transactional Outbox

所有需要可靠发布的状态/领域事件 SHOULD 使用 outbox：

```text
business row change + outbox insert = same local transaction
publisher asynchronously sends
consumer idempotently applies
```

Outbox 至少包含：

```text
outbox_id
event_id
event_type
event_version
aggregate_ref
aggregate_revision
payload
created_at
published_at/null
attempt_count
```

## 16. Queue Consumer State

消费者必须保存 dedup/revision 或使处理天然幂等。Broker ack 只能在本地事务成功后发生。

Poison event 进入 DLQ/parking，不得无限重试阻塞同 partition。

## 17. Telemetry / Audit / Artifact Storage

### Telemetry

```text
Metrics -> observability backend
Traces -> tracing backend
Logs -> log backend
Run Summary/Fingerprint -> projection store
```

### Audit

Audit 使用独立完整性/保留边界，不能因普通 telemetry 成本策略删除。

### Artifact

大型工件、候选 bundle、SBOM、sampled payload、cold evidence 进入 object/artifact storage；数据库保存 refs/digest/metadata。

## 18. Retention

必须区分：

```text
authoritative business state retention
Audit/legal retention
Telemetry retention
sampled trace retention
Evolution active working set retention
Artifact retention
Projection rebuild lifecycle
```

不得用统一 TTL 删除所有数据。

## 19. Migration

数据库 migration MUST：

- 有版本；
- 可在 CI/预生产验证；
- 不允许 destructive migration 无备份/回滚策略；
- 与 ReleaseCandidate / ReleaseManifest 中 migration refs 对齐；
- 长运行 Run 的兼容性必须显式处理。

## 20. Codex 实施规则

Codex MUST：

1. 先区分 authoritative table 与 projection table；
2. 不因查询方便复制第二份权威状态；
3. 所有关键更新使用 revision/CAS；
4. 所有副作用先建立 ActionRecord；
5. 所有需要可靠事件的事务使用 outbox；
6. 不把远程 API 调用包在数据库事务中；
7. 不用 ORM cascade 隐式跨模块删除领域事实；
8. 为 tenant isolation、duplicate action、stale fencing、outbox replay 编写自动测试。

## 21. 完成定义

本包完成至少意味着：

- 每个 Canonical/权威对象有明确持久化位置；
- Projection 与 authority 明确区分；
- Run/Action/Evolution/Release 事务边界清晰；
- CAS/fencing/idempotency/outbox 有实现规则；
- Telemetry/Audit/Artifact 没有被错误合并为一个数据库；
- Codex 不需要自行设计核心一致性模型。
