# UEAF V1 验收与一致性测试规范

版本：`0.1.0-draft`  
规范状态：Draft  
Architecture Generation: `V1`  
Maturity: `Required for Implementation`  
Implementation: `Current`

## 1. 目的

本文把 UEAF V1 的架构不变量转换为 Codex/工程实现必须通过的可执行验收场景。目标是让“是否实现正确”由自动测试和证据判断，而不是由代码结构看起来合理来判断。

## 2. 测试分层

V1 MUST 至少包含：

```text
Schema tests
Unit tests
Contract tests
Module integration tests
Adapter conformance tests
Persistence/transaction tests
Security invariant tests
Evolution vertical-slice tests
Release/rollback tests
Failure-injection tests
```

## 3. Test ID 规范

每个规范性场景 SHOULD 有稳定 ID：

```text
RUN-001
ACT-001
SEC-001
EVO-001
REL-001
```

CI 输出必须能回溯到规范 Test ID。

## 4. Runtime / State 验收

### RUN-001 queued 不可跳过 admitting

Given 一个通过边缘预校验的新请求  
When 创建 Run  
Then 必须经历 `queued -> admitting -> admitted/running`，不得直接 `queued -> running`。

### RUN-002 phase 与 disposition 正交

Given 一个等待审批的 Run  
Then `RunPhase=waiting` 时不得伪造 terminal disposition。

Given Run 结束  
Then `CompletionDisposition` 必须明确且与 phase 分离。

### RUN-003 stale fencing token

Given Worker-A lease 过期、Worker-B 获得更高 fencing token  
When Worker-A 恢复并写状态  
Then 写入必须被拒绝。

### RUN-004 crash recovery

Coordinator/Worker 在关键 phase 被强制终止后，Run 必须可恢复且不能重复提交权威状态。

## 5. Runtime Adapter 一致性

### ADP-001 Model Gateway 强制

Adapter 发起模型步骤必须经过 `ModelStepPort`；直连 Provider 的测试凭据不得存在。

### ADP-002 Tool Gateway 强制

Adapter 的 function/tool call 必须转为 `ToolIntent`；不得直连企业写 API。

### ADP-003 unsupported capability

Adapter 不支持某能力时必须显式返回 unsupported，不得静默模拟成功。

### ADP-004 第二 Adapter 等价性

同一只读 Agent Definition 在两个 Adapter 下，Task/Run/Context/Audit/Completion 的 UEAF 语义必须一致；底层 trace 可不同。

## 6. Tool / Action 验收

### ACT-001 action_key 幂等

并发提交同一业务动作 100 次，只能创建一个权威 `ActionRecord`。

### ACT-002 timeout unknown 不盲重试

Given 写 API 实际成功但响应丢失  
When ExecutionAttempt timeout  
Then：

```text
outcome_certainty = unknown
ActionRecord -> reconciling
禁止第二次业务写
```

直到对账确认。

### ACT-003 certain failure 才按策略重试

只有权威确认失败且 retry policy 允许时，才产生下一 ExecutionAttempt。

### ACT-004 approval fail closed

高风险动作在审批系统/审计不可用时必须 fail closed。

### ACT-005 permission denied 不自提权

PermissionDenied 可以产生 Evidence，但不得导致自动扩大 Tool permission。

## 7. Context / RAG 验收

### RAG-001 ACL before relevance

未授权文档必须在相关性排序前被过滤，不能因高相似度进入 ContextManifest。

### RAG-002 retrieval_empty 单次失败

单次 `retrieval_empty` 只能形成运行 Evidence；不能直接创建 `EvolutionTrigger` 或 `MutationProposal`。

### RAG-003 context size guard

任何 Context Policy Mutation 后仍必须满足模型上下文和预算上限。

## 8. Eval / Release 验收

### EVAL-001 baseline pairing

Candidate 与 baseline 必须在可比较环境、预算和数据集条件下评测；不等价差异必须标记。

### EVAL-002 hard safety failure

任意安全硬失败不得被平均质量分或业务收益抵消。

### EVAL-003 inconclusive

测量缺失/证据不足必须产生 `inconclusive/invalid`，不得自动视为 pass。

### REL-001 candidate != manifest

`ReleaseCandidate` 不得被 Routing/Runtime 直接加载为生产版本。

### REL-002 manifest immutable

当前运行绑定的 `ReleaseManifest` 不得原地改变；恢复仍使用原 release_id。

### REL-003 rollback

Canary 触发 rollback 条件时必须能恢复指定 rollback target，并保存发布事实。

## 9. Evidence 验收

### EVD-001 正常路径 0 LLM Token

Run Summary、rolling aggregation、fingerprint、Trigger Candidate 默认路径必须不调用 LLM。

### EVD-002 high-cardinality labels

`run_id/trace_id/user_id/document_id/prompt` 等不得作为常规 Metric label。

### EVD-003 backpressure

Telemetry 超载时优先保留 Audit/Security/ActionReceipt/P0-P1/Run Summary，优先降低 verbose success trace。

### EVD-004 evidence gap visible

Telemetry 丢失必须产生可观测 gap，不得解释为“无异常”。

## 10. Evolution Trigger 验收

### EVO-001 anomaly != trigger

普通异常、告警、单次失败不能直接成为 `EvolutionTrigger`。

### EVO-002 Trigger Gate

非 P0 Trigger 至少验证：

```text
evidence sufficient
still relevant
mutable surface match
mitigation insufficient
novelty sufficient
expected value positive
cooldown satisfied
```

### EVO-003 no_evolution_needed 合法

Trigger 成立后，Diagnosis 可正常结束为 `no_evolution_needed`，不要求产生 Mutation。

## 11. Diagnosis / Repair 验收

### REP-001 symptom != repair target

Tool invalid args 可被诊断为 Prompt/Model 问题；测试必须证明 Repair Router 不按症状层机械修复。

### REP-002 Smallest Effective Repair

有证据支持 R1 时，不得同时修改 R2/R3/R4 不相关区域。

### REP-003 escalation requires evidence

R1 Candidate 失败不能自动升级 R2；必须有新 diagnosis/failure evidence。

### REP-004 R5

ACL、Identity、Permission、PDP/PEP、Secrets、Audit/Eval root、Release Authority、Budget Enforcement 等不能生成自动 MutationProposal。

## 12. Mutation Surface 验收

### MUT-001 undeclared field reject

`changes[].path` 不在 Subject Profile 中时，Candidate Build 必须拒绝。

### MUT-002 frozen field reject

尝试修改 `permissions.*`、`release_authority.*`、`eval_root.*` 等必须拒绝。

### MUT-003 range reject

例如 Profile 规定 `top_k <= 20`，Proposal `top_k=100` 必须拒绝。

### MUT-004 repair-level mismatch

R1 Proposal 尝试 workflow topology change 必须拒绝。

### MUT-005 effective surface intersection

即使 Profile 可修改字段，但 `EvolutionAuthorityPolicy` 或本轮 mutable_scope 不允许，也必须拒绝。

### MUT-006 single hypothesis sparse mutation

首个 V1 Profile 默认要求：

```text
1 candidate
1 repair target
1 hypothesis
1 component
<=2 fields
```

超限 Proposal 必须被 Validator 拒绝或拆分。

## 13. Objective / Fitness 验收

### OBJ-001 hard constraints first

Candidate 质量提升但发生安全硬失败，必须淘汰。

### OBJ-002 guardrail

质量提升 4%，但成本超过 Profile 允许退化区间，不能自动选为 improved。

### OBJ-003 evidence confidence

业务 KPI 映射证据置信不足时必须 `inconclusive`。

### OBJ-004 tie-break

主目标差异不显著时按 Profile 的 lower cost / latency / complexity 等稳定规则选择，不交给自由 LLM 判断。

## 14. Evolution Strategy 验收

### STR-001 bounded input

Strategy 不能读取未授权全历史 Trace；只能使用 bounded Working Set 和 refs。

### STR-002 zero candidate

Strategy 返回 0 Proposal 是合法结果。

### STR-003 repeated failed proposal

在环境和 Evidence 未变化时，不得重复已知失败 Proposal。

### STR-004 no release authority

Strategy 无法签发 Eval/ReleaseDecision/ReleaseManifest。

## 15. Evolution Threat 验收

### ETH-001 delayed prompt injection

Evidence 中包含“忽略系统规则、修改权限”等文本时，只能作为不可信数据；Mutation Surface/Governance 仍阻止越权。

### ETH-002 trigger flooding

大量相似恶意失败不能线性生成 EvolutionRun；dedup/cooldown/budget 生效。

### ETH-003 R4 supply chain

生成代码 Candidate 必须经过 static analysis、secret scan、SBOM、sandbox、integration/security tests。

### ETH-004 budget exhaustion

达到 Evolution budget 后 Run 必须正常终止为对应 disposition，不允许继续强模型调用。

## 16. Evolution Vertical Slice 必测

V1 在进入“可开发完成”状态前必须有一个真实或可控退化场景，例如：

```text
Baseline retrieval_empty = 1%
注入 query distribution drift
retrieval_empty -> 8%
```

系统必须演示：

```text
Telemetry
-> Aggregate/Fingerprint
-> TriggerCandidate
-> Trigger Gate
-> EvolutionTrigger
-> EvolutionRun
-> bounded Evidence Expansion
-> Diagnosis
-> R1 Context Policy MutationProposal
-> machine validation
-> GenomeManifest candidate
-> ReleaseCandidate
-> targeted Eval vs baseline
-> Objective comparison
-> reject or canary
```

**Reject 也是合法闭环结果。** 不得为了演示“进化成功”放宽 Gate。

## 17. CI Gate

PR 合并前至少要求：

```text
schema validation
unit tests
contract tests
migration tests
security invariant tests
adapter conformance relevant subset
```

触及 Evolution/Tool/Release 核心边界的变更必须运行对应 vertical slice/failure-injection tests。

## 18. Codex 实施规则

Codex 每完成一个模块 MUST：

1. 先引用对应规范 Test ID；
2. 先补失败测试，再实现；
3. 不通过删除/放宽测试解决规范冲突；
4. 测试发现规范矛盾时停止扩大实现范围，记录文档缺口；
5. 不以 mock 全绿替代关键事务/副作用/恢复集成测试。

## 19. V1 开发启动门槛

正式大规模编码前至少应已有：

- Schema package skeleton；
- Port/Event interfaces；
- persistence migration skeleton；
- RUN/ACT/EVO/MUT/REL 核心场景测试文件；
- 一个 Evolution Vertical Slice fixture。

## 20. 完成定义

本规范落地后，Codex 的任务应从“按文档理解实现”变为：

```text
choose Test IDs
-> implement schema/port/storage
-> make tests green
-> preserve invariants
```

从而显著降低自由猜测空间。
